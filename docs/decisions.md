## D-001 기술 스택

- **상태:** 승인
- **결정:** React + TypeScript + Vite로 만들고, 테스트는 Vitest, 콘텐츠와 세이브 검증은 Zod, 로컬 저장은 IndexedDB를 쓴다.
- **이유:** 바이브 코딩에서 AI가 가장 안정적으로 다루는 조합이다. Vitest는 Vite 설정을 그대로 쓰고, Zod 스키마에서 TypeScript 타입을 만들 수 있어 데이터 구조의 기준을 하나로 둘 수 있다.
- **대안:** 게임 엔진(Phaser 등)은 텍스트·기호 중심 게임에 비해 과하다. Canvas 직접 구현은 UI 패널이 많은 이 게임에 불리하다.
- **재검토 조건:** 격자 맵 렌더링 성능이 CSS Grid로 부족할 때 Canvas 도입을 검토한다.

## D-002 저장은 브라우저 우선, 서버에는 사본

- **상태:** 승인
- **결정:** 게임은 IndexedDB를 주 저장소로 쓰고, 서버에는 백업과 기기 간 동기화용 사본만 둔다. 이동과 전투는 행동 단위로 서버에 보내지 않는다.
- **이유:** 서버 없이도 게임이 완결되어야 하고(명세 1.3절), 서버 비용과 부하를 최소로 줄일 수 있다.
- **대안:** 서버 중심 저장은 비용과 구현량이 크고, 오프라인 플레이가 어렵다. 브라우저 저장만 쓰면 기기 이동이 안 되고, 아이폰 사파리의 7일 저장 데이터 삭제 규칙으로 진행이 사라질 수 있다.
- **재검토 조건:** 플레이어 간 경제나 경쟁 요소를 도입할 때.

## D-003 서버는 Cloudflare 최소 구성

- **상태:** 승인
- **결정:** 정적 사이트는 Cloudflare Pages, 서버 함수는 Workers, 데이터베이스는 D1(SQLite)을 쓴다. 명세 v1.1의 Node.js와 PostgreSQL을 대체한다.
- **이유:** 무료 범위가 넓고, 무료 한도를 넘으면 요금 대신 오류가 반환되어 예상치 못한 비용이 생기지 않는다. 상시 켜진 서버가 없다.
- **대안:** Supabase는 인증과 데이터베이스를 함께 주지만, 무료 프로젝트가 활동이 없으면 자동으로 멈추고 유료 플랜이 더 비싸다.
- **재검토 조건:** 요금제가 바뀌거나, 하루 활동 인원이 무료 한도를 꾸준히 넘을 때. 서버 작업 착수 시 요금을 다시 확인한다.

## D-004 결정론적 엔진

- **상태:** 승인
- **결정:** 게임 규칙은 React와 분리된 순수 로직이다. 상태 변경은 `dispatch`를 거치고, 시간은 런타임이 주입하며, 난수는 상태에 저장된 시드 난수로만 얻는다.
- **이유:** 규칙을 UI 없이 자동 테스트할 수 있고, 오프라인 경과를 실시간과 같은 경로로 처리할 수 있으며, 구울 토벌 기록을 재생해 검증할 수 있다.
- **대안:** UI 컴포넌트 안에서 규칙을 처리하면 처음엔 빠르지만, 테스트와 재현이 어렵고 세션이 바뀔 때마다 구조가 흔들린다.
- **재검토 조건:** 없음. 이 결정을 바꾸려면 아키텍처 전체를 다시 검토해야 한다.

## D-005 플레이어 간 거래·PvP·순위 없음

- **상태:** 승인
- **결정:** 플레이어 간 거래, PvP, 순위 경쟁을 만들지 않는다. 서버는 게임 결과를 검증하지 않고, 공유 기록을 저장하고 보여 주기만 한다. 구울 공식 토벌은 먼저 기록된 1건만 인정하고 전투 기록을 보관한다.
- **이유:** 세이브 조작의 피해가 본인에게만 돌아가므로 서버 검증이 필요 없다. 서버 구현량과 비용이 크게 줄어든다.
- **대안:** 서버 권위 구조는 모든 행동을 서버가 검증해야 해서 이 프로젝트 규모에 맞지 않는다.
- **재검토 조건:** 순위나 거래 기능을 넣고 싶어질 때. 그때는 해당 기능의 결과가 조작될 수 있음을 먼저 검토한다.

## D-006 `src/runtime/` 디렉터리 신설

- **상태:** 승인
- **결정:** 틱 루프, 일시정지, 하트비트, `visibilitychange`, 자동 저장 예약, `GameStore`를 `src/runtime/`에 둔다.
- **이유:** 엔진은 브라우저 API를 쓸 수 없고, UI는 게임 규칙을 처리하면 안 된다. 둘을 잇는 브라우저 의존 코드가 들어갈 곳이 필요하다.
- **대안:** `src/ui/` 안에 두면 UI와 시간 처리가 섞여 테스트가 어려워진다.
- **재검토 조건:** 없음.

## D-007 수치 수정치 계산 순서

- **상태:** 승인
- **결정:** 기본값 → `add` 합산 → `mul` 곱셈 → 반올림 → 최소·최대 제한. 모든 수치 계산은 `computeValue`를 거친다.
- **이유:** 순서를 하나로 고정하면 어떤 효과가 추가돼도 결과가 흔들리지 않는다. 배율을 곱셈으로 합치면 감면이 여러 개 겹쳐도 0 이하로 떨어지지 않는다.
- **대안:** 퍼센트를 더한 뒤 한 번에 곱하는 방식은 감면이 겹치면 값이 0이 되기 쉽다.
- **장단점:** 단순하고 예측 가능하다. 대신 "다른 배율을 무시한다" 같은 특수 효과는 표현할 수 없다.
- **재검토 조건:** 기획상 이 순서로 표현할 수 없는 효과가 필요해질 때.

## D-008 난수 알고리즘 sfc32

- **상태:** 승인
- **결정:** sfc32를 의존성 없이 `src/engine/core/rng.ts`에 직접 구현한다. 내부 상태(32비트 정수 4개)는 `meta.rngState`에 저장한다.
- **이유:** 짧은 코드로 구현할 수 있고, 내부 상태를 저장·복원하기 쉬우며, 게임 용도로 품질이 충분하다.
- **대안:** 외부 난수 라이브러리는 의존성이 늘고 내부 상태 저장 방식이 제각각이다.
- **재검토 조건:** 난수 품질 문제가 실제로 발견될 때.

## D-009 불변 상태 갱신은 직접 작성

- **상태:** 승인
- **결정:** 새 상태는 바뀐 부분만 새로 만드는 코드를 직접 작성한다. Immer는 쓰지 않는다.
- **이유:** 의존성을 늘리지 않는다. 초기 상태 구조가 작아 직접 작성으로 충분하다.
- **대안:** Immer는 깊은 중첩 갱신이 편하지만 의존성이 늘고, 실수로 원본을 바꾸는 코드와 구분하기 어려워질 수 있다.
- **재검토 조건:** 갱신 코드가 반복적으로 길어지거나, 갱신 실수로 인한 버그가 생길 때.

## D-010 자동 저장 방식

- **상태:** 임시
- **결정:** 행동이 처리되면 1초 디바운스 후 저장하고, 화면이 가려질 때(`visibilitychange`)는 즉시 저장한다. 새 세이브를 쓰기 전에 직전 세이브를 백업 슬롯 1개에 보관하고, 새 세이브를 읽지 못하면 백업을 불러온다.
- **이유:** 행동마다 바로 쓰면 IndexedDB 쓰기가 지나치게 잦다. 백업 1개로 저장 도중 오류에 의한 세이브 손상을 막는다.
- **장단점:** 브라우저가 비정상 종료되면 마지막 1초 이내의 진행을 잃을 수 있다.
- **재검토 조건:** 플레이테스트에서 진행 손실이나 저장 지연이 체감될 때.

## D-011 시간 관련 값

- **상태:** 임시
- **결정:**

| 값 | 임시값 | 위치 |
|---|---|---|
| 1틱의 실제 길이 | 10초 | 콘텐츠의 시간 규칙 |
| 하트비트 간격 | 15초 | 런타임 설정 |
| 하트비트 유예 시간 | 2분 | 런타임 설정 |
| 최대 오프라인 인정 시간 | 24시간 | 콘텐츠의 시간 규칙 |

- **이유:** 브라우저는 백그라운드 탭의 타이머를 1분 단위까지 늦출 수 있으므로 유예 시간은 그보다 길어야 한다. 1틱 10초는 회복 표시가 너무 느리지 않으면서 위험지대 습격 판정 횟수를 다루기 쉬운 크기다. 최대 오프라인 인정 시간은 스태미나가 가득 차는 시간보다 충분히 길면 되고, 방치 작업 완료 판정에는 영향을 주지 않는다.
- **재검토 조건:** 플레이테스트에서 회복·습격 체감이 어색하거나, 백그라운드 탭이 정지로 잘못 판정될 때.

## D-012 스태미나 내부 소수 허용

- **상태:** 대체됨 (D-014)
- **결정:** 스태미나 내부 값은 소수를 허용하고, 화면에는 내림해서 보여 준다. 이동 비용 비교는 내부 값으로 한다.
- **이유:** 1틱 10초 기준으로 틱당 회복량이 소수가 된다(예: 분당 2 회복이면 틱당 약 0.33).
- **대안:** 회복 누적 칸을 따로 두고 정수만 저장하는 방식은 상태 필드가 하나 늘고 계산이 복잡해진다.
- **재검토 조건:** 부동소수점 오차로 경계값 문제가 생길 때. 그때는 정수 단위(예: 스태미나 1 = 내부 100)로 바꾼다.

## D-013 미정 세부 사항은 임시값으로 진행

- **상태:** 승인
- **결정:** 수치, 간격, 문구 같은 세부 사항이 미정이라는 이유로 구현을 멈추지 않는다. 합리적인 임시값을 골라 기록하고 진행하며, 플레이테스트 후 사용자가 확정한다. 핵심 게임 규칙과 기획 방향은 여전히 확인을 받는다.
- **이유:** 프로토타입에서 실제로 굴려 봐야 정할 수 있는 값이 많다. 값이 정해지기를 기다리면 개발이 멈춘다.
- **기록 위치:** 구조나 여러 시스템에 영향을 주는 값은 이 문서에, 그 밖의 임시값은 `docs/progress.md`의 '임시값' 목록에 적는다. `CLAUDE.md` 7절에 같은 규칙이 있다.

## D-014 스태미나는 정수로 유지

- **상태:** 임시 (값은 플레이테스트 후 확정)
- **결정:** 스태미나와 모든 회복량·비용은 정수로 다룬다. 소수가 생기지 않도록 최대치와 틱당 회복량을 정수 단위로 맞추고, 이동 비용도 같은 비율로 조정한다. D-012를 대체한다.

| 값 | 임시값 | 비고 |
|---|---|---|
| 1틱의 실제 길이 | 10초 | D-011과 같음 |
| 최대 스태미나 | 900 | 명세 예시 300의 3배 |
| 거점·야영지 회복 | 틱당 1 (분당 6) | 0에서 가득 차기까지 150분 |
| 위험지대 대기 회복 | 틱당 1 (분당 6) | 거점과 같은 속도지만 틱마다 습격 판정 |
| 위험지대 휴식 회복 | 틱당 5 (분당 30) | 거점의 5배. 0에서 가득 차기까지 30분, 10분 휴식에 300 |
| 미탐사 경로 이동 비용 | 6 | 명세 예시 2의 3배 |
| 탐사 완료 경로 이동 비용 | 3 | 미탐사의 절반 (`mul 0.5`) |
| 안전지대 이동 비용 | 0 | |

- **이유:** 소수 스태미나는 부동소수점 오차와 경계값 비교 문제를 만든다. 정수 단위로 맞추면 상태와 테스트가 단순해진다. 최대치를 3배로 늘린 만큼 이동 비용도 3배로 늘려, 가득 찬 스태미나로 다닐 수 있는 거리는 명세 예시(미탐사 150칸)와 같게 유지했다.
- **대기 회복 속도:** 틱당 정수라는 조건에서 대기를 거점보다 느리게 하려면 거점이 틱당 2 이상이어야 해서 모든 수치가 더 커진다. 그래서 대기는 거점과 같은 속도로 두고, 습격 위험으로 차이를 둔다. 휴식·음식에 비해서는 여전히 느린 보조 수단이다.
- **대안:** 내부 단위를 쪼개는 방식(스태미나 1 = 내부 100)은 소수를 피할 수 있지만 표시와 계산 사이에 변환이 생긴다.
- **재검토 조건:** 플레이테스트에서 회복이나 이동 비용 체감이 어색할 때. 값을 바꿀 때도 정수 조건은 유지한다.

## D-015 개발 환경과 Pages 미리보기

- **상태:** 대체됨 (D-018). 개발 도구 선택을 변경했으며 Git·Pages 운영 방식은 D-018에서 유지한다.
- **결정:**
  - 개발은 주로 Claude Code on the web(클라우드 세션)에서 한다. 저장소는 GitHub 비공개 저장소이고, 작업 결과는 작업 브랜치와 PR로 올린다. `main` 병합은 사용자가 한다.
  - Cloudflare Pages를 GitHub 저장소에 연결해, 변경이 올라올 때마다 미리보기 주소가 자동으로 만들어지게 한다. 빌드 명령은 `npm run build`, 출력 폴더는 `dist`다. 연결은 S0에서 프로젝트를 생성한 직후 사용자가 한다.
  - 주소는 Pages 기본 주소(`*.pages.dev`)를 쓴다. 사용자 도메인 연결과 접근 제한 기능은 쓰지 않는다.
- **이유:** 사용자는 주로 폰에서 작업을 확인한다. 클라우드에서 실행되는 개발 서버는 폰에서 열 수 없고, 빌드 파일을 내려받아 파일로 여는 방식은 실제 웹 환경과 저장·시간 처리가 다르게 동작할 수 있다. Pages 미리보기는 실제 배포와 같은 https 환경에서, 변경마다 자동으로 갱신된다. 정적 사이트라 비용이 없다(D-003, 명세 15.8절의 P0~P1 구성과 같음).
- **대안:** 한 파일 빌드를 내려받아 여는 방식은 아이폰에서 동작하지 않고, IndexedDB와 시간 처리 테스트를 믿을 수 없다.
- **장단점:** 미리보기 주소는 주소를 아는 사람이면 누구나 열 수 있다. 주소를 공유하지 않는 것으로 관리한다.
- **재검토 조건:** 미리보기를 외부에 공개하지 않아야 할 이유가 생기거나, 사용자 도메인이 필요해질 때(S10).

## D-016 Node 실행 스크립트는 Node 내장 TypeScript 실행

- **상태:** 승인
- **결정:**
  - `npm run validate:content` 같은 Node 실행 스크립트는 별도 실행 도구 없이 Node 내장 TypeScript 실행(Node 22.18 이상에서 플래그 없이 동작)으로 돌린다.
  - 스크립트는 루트 `scripts/`에 둔다. `scripts`는 `content`와 `engine`을 import할 수 있고, `src/`는 `scripts`를 import하지 않는다.
  - 이를 위해 모든 TypeScript 코드는 상대 import에 확장자를 붙이고, `import type`을 쓰며, `enum`·`namespace`·생성자 매개변수 프로퍼티를 쓰지 않는다. `tsconfig.json`(`nodenext`, `verbatimModuleSyntax`, `erasableSyntaxOnly`)이 강제한다 (architecture 1.4절).
- **이유:** 새 의존성이 없다. architecture 6장의 "같은 검증 코드를 Node에서 실행한다"를 그대로 따른다. 검증 CLI는 효과 레지스트리(`engine/core`)도 써야 하는데, `content`는 Zod 외에 프로젝트 모듈을 import할 수 없어서(architecture 1.2절) `src/content/` 밖에 둔다.
- **대안:** Vitest로 실행하면 import 규칙은 그대로지만 출력이 테스트 형식이고 `npm test`와 범위를 나눠야 한다. `tsx` 패키지는 가장 간편하지만 새 의존성이다.
- **장단점:** 의존성 없이 단순하다. 대신 import 표기 규칙이 프로젝트 전체에 생기고, Node 22.18 미만에서는 스크립트가 실행되지 않는다 (`package.json`의 `engines`, `.node-version`에 명시).
- **재검토 조건:** Node 내장 실행으로 처리할 수 없는 문법이나 도구가 필요해질 때.

## D-017 코어 처리기 연결과 효과 검증

- **상태:** 승인 (S0 세 번째 단위 제안 승인)
- **결정:**
  - 코어는 시스템을 import하지 않는다. 연결부가 시작할 때 `createDispatcher(handlers)`를 호출해 `dispatch(state, action, ctx)` 형태의 함수를 만든다.
  - 행동·사건의 구체적인 유니온은 시스템별로 정의하고 타입 인수로 전달한다. 행동 종류별 처리기 매개변수 타입은 `ActionHandlers`로 연결한다.
  - 행동 처리기 목록과 개별 처리기는 복사·동결하며 실행 중 등록·제거 기능을 만들지 않는다. 제품의 기본 행동 목록은 S0에서 비어 있다.
  - 효과는 `defineEffect`로 Zod 스키마와 적용 함수를 묶고 `createEffectRegistry`로 고정된 목록을 만든다. 레지스트리는 원시 매개변수를 검증·파싱한 후 적용한다.
  - 콘텐츠를 불러올 때 같은 레지스트리의 검증 함수를 호출한다. 콘텐츠 로더 연결은 S0 네 번째 단위에서 구현한다.
  - 테스트용 행동·효과는 테스트 구성에서만 등록한다. 코드 예외는 일반적인 행동 거부로 숨기지 않는다.
- **이유:** 코어의 의존 방향과 고정 목록 원칙을 지키면서, 실제 시스템이 없는 S0에서도 성공·거부·난수·효과 실행 경로를 검증할 수 있다.
- **대안:** 코어가 시스템을 직접 import하면 의존 방향을 위반한다. 실행 중 등록하는 구조는 필요 이상의 상태와 수명 관리가 생긴다.
- **장단점:** 연결부에서 목록을 조합하는 절차가 필요하지만, 시스템별 행동 유니온의 타입 검사와 독립 테스트가 가능하다. 동적으로 바뀌는 플러그인 구조는 지원하지 않는다.
- **재검토 조건:** 실행 중 시스템을 교체해야 하는 실제 요구가 생길 때.

## D-018 개발 도구 선택과 Git·미리보기 운영

- **상태:** 승인 (사용자 지시, 2026-10-14). D-015를 대체한다.
- **결정:**
  - GPT에서 구현·실행·테스트·디버깅을 우선 진행한다. 사용할 수 있는 실행 환경에서 실제 검증한다.
  - Claude Code 사용은 실행 환경 접근, 브라우저 확인 등 구체적인 비교우위가 확인될 때만 제안한다. 제안에는 넘길 작업 범위와 이쪽에서 해결하기 어려운 이유를 적는다.
  - 해결되지 않은 검증은 그대로 미검증으로 보고한다. 도구를 바꿨다는 이유로 완료 기준을 줄이지 않는다.
  - 결과는 GitHub 작업 브랜치와 PR로 전달하고, `main` 병합은 사용자가 한다. 두 도구가 같은 브랜치를 동시에 수정하지 않는다.
  - Cloudflare Pages 운영은 D-015의 설정을 유지한다: `main` 운영 빌드, 다른 브랜치 미리보기, 빌드 명령 `npm run build`, 출력 `dist`, 기본 Pages 주소 사용.
- **이유:** Claude Code 사용량이 빠르게 소모되는 상황에서 반복 구현·검증을 GPT로 옮기고, 필요한 경우에만 Claude Code를 사용한다.
- **재검토 조건:** 도구의 실행 환경·권한·사용량 조건이 달라질 때.

## D-019 콘텐츠 기반과 실행 환경의 연결

- **상태:** 승인 (네 번째 콘텐츠 단위 진행 위임)
- **결정:**
  - 매니페스트가 버전·시간 규칙 파일·정의 파일 목록을 명시한다. 누락·중복·목록 외 파일은 로딩 오류로 처리한다.
  - 시간·스태미나·하트비트 임시값은 기존 D-011·D-014 그대로 JSON에 저장한다. 이번에 계산 규칙이나 값을 바꾸지 않는다.
  - S0 공통 정의 외피는 id·references·dependsOn·effects다. 일반 참조는 존재만 검증하고, 선행 의존은 순환도 검증한다. 게임별 데이터 필드는 각 시스템에서 정의한다.
  - content는 같은 계층과 Zod만 사용한다. 효과 검증 함수는 연결부가 전달하며 로딩 중 효과를 실행하지 않는다.
  - 브라우저 연결부는 Vite로, Node CLI는 파일 시스템으로 JSON을 수집한다. 두 경로가 같은 순수 로더와 제품 효과 레지스트리 검증 함수를 쓴다.
  - 하나라도 검증 실패하면 부분 DB를 반환하지 않는다. 성공한 DB는 입력과 분리한 뒤 중첩까지 읽기 전용으로 고정한다.
- **이유:** 잘못된 콘텐츠가 실행 단계에 들어가지 않게 하고, 엔진을 import하지 않는 콘텐츠 계층과 브라우저·CLI의 같은 검증 경로를 유지한다.
- **장단점:** 매니페스트에 파일을 추가해야 한다. 대신 검증에서 누락되는 파일과 잘못된 의존 관계를 찾을 수 있고, 데이터 파일 추가만으로 브라우저·CLI가 함께 수집한다.
- **재검토 조건:** 실제 게임별 정의를 도입할 때 공통 외피와 참조 추출 구조를 확장한다. 선택적 의존이나 순환을 허용해야 하는 관계는 dependsOn과 구분한다.


## D-020 최초 세이브 계약과 복원 경계

- **상태:** 승인 (S0 다섯 번째 단위 계속 진행 위임)
- **결정:**
  - 최초 SaveFile은 schemaVersion 1이며 문서의 7개 필드를 유지한다. 타입은 Zod 스키마에서 추론하고 상태는 기존 코어 GameState 계약을 사용한다.
  - 저장 경계의 상태 스키마는 persistence에 둔다. 엔진의 공개 상태·dispatch 계약이나 의존 방향을 변경하지 않는다.
  - saveId·revision·savedAt·contentVersion은 호출부가 주입한다. 직렬화·복원 자체는 게임 난수·시간·revision을 변경하지 않는다. 실제 저장마다 revision을 올리는 호출부는 S3에서 구현한다.
  - 객체와 JSON 불러오기는 같은 형식·변환·검증 경로를 사용하며, 입력과 분리한 JSON 데이터만 처리한다. 미정의 필드나 손상된 값은 삭제·강제 변환 대신 거부한다.
  - 현재 구조 버전은 1이고 실제 변환은 없다. 체인은 정확히 1버전씩 증가해야 하며 누락·중복·미래 버전·변환 실패를 거부한다. 실제 구조 변경은 기존 규칙대로 사용자 승인과 이전 세이브 예시·왕복 테스트를 요구한다.
  - 콘텐츠 버전은 저장된 값을 보존한다. 콘텐츠 호환성 정책은 실제 콘텐츠 변경 시 정의하며 구조 버전 변환과 구분한다.
  - CombatLog는 타입만 정의한다. 실제 전투 행동·초기 전투 상태·재현은 S5다. IndexedDB·자동 저장·백업은 S3다.
- **이유:** 저장·불러오기만으로 시간이나 난수가 진행되는 문제를 막고, 손상된 상태를 엔진 실행 전에 차단한다. 최초 형식에 존재하지 않는 이전 버전이나 브라우저 저장 기능을 추가하지 않는다.
- **재검토 조건:** 시스템별 상태 필드를 추가하거나 실제 세이브 구조·콘텐츠 호환성을 변경할 때.

## D-024 확인한 벽의 지도 유지와 맵 색상

> 2026-10-15: 벽 유지/표현은 최신 사용자 와이어프레임의 D-040으로 대체됨. 아래는 당시 결정 기록이다.

- **상태:** 승인 (사용자 변경 요청, 2026-10-14). D-022의 시야 밖 벽 재가림 규칙만 대체한다.
- **결정:**
  - 한 번 확인한 벽은 현재 시야 밖에서도 지도에 남긴다. 아직 보지 않은 벽은 공개하지 않는다.
  - 현재 칸·인접 네 칸의 시야와 보기만 한 바닥의 재가림은 유지한다.
  - 이미 밟은 칸은 모두 현재 시야의 중심이었던 칸이다. 그 칸들과 인접한 벽을 같은 맵·층의 기록에서 계산해 시야 밖에서는 explored로 반환한다. 검정색 벽 표시는 visible·explored에 동일하게 적용한다.

  - 기본 지도 배경은 짙은 회색, 벽은 검정색이다. 현재 시야·밟은 바닥·플레이어와 범례 색상도 함께 구분한다. 구체 색상 값은 progress의 임시값에 기록한다.
- **이유:** 벽이 시야에서 사라져 길을 파악하기 어렵다는 사용자 피드백을 반영한다.
- **대안:** 별도 본 벽 기록을 추가하면 현재 고정 시야에서는 길 기록과 중복되며 저장 구조 변경도 필요하다.
- **재검토 조건:** 시야 범위가 넓어지거나 벽·문이 동적으로 바뀌어 길 기록만으로 실제 확인 이력을 복원할 수 없게 될 때.

## D-026 S2 실시간 루프와 세션 정지 연결

- **상태:** 구현 (기존 시간/정지 명세와 사용자의 “ㅇㅋ. 계속 진행.” 위임에 따른 두 번째 단위)

- **공백/정지:** 위험 구역의 유예 초과 공백은 처리 전 제외하고 명시적 재개를 기다린다. 설정창 닫기는 기존 수동/공백 정지를 유지한다. 재개는 정지 구간과 부분 틱을 소급하지 않고 새 틱을 시작한다. 안전 구역의 열린 세션은 실시간 지연을 처리하며 닫힌 창 정산은 S3다.
- **이동:** D-013에 따라 minimumMoveIntervalMs=200을 임시로 JSON에 추가했다. 성공한 이동만 간격을 소비하며 키보드/모바일 입력이 공유한다. 입력 폭주를 줄이면서 조작 반응을 유지하기 위한 출발값이다. 콘텐츠 버전 0.2.1, 맵 버전 1. 이전 세이브 예시·버전 변환은 보존한다.
- **타이머:** 시작/종료 멱등·취소 세대 검사로 StrictMode와 늦은 콜백의 중복 틱을 방지한다. 프로젝트 의존성은 추가하지 않았다.
- **재검토 조건:** 실제 모바일 공백/재개·이동 체감 플레이, 휴식/습격 도입 시 배치 틱과 정지 검사, S3에서 정산 시각과 실시간 중복 방지 연결.


## D-027 플레이 검증용 틱 2초와 회복 조건 표시

- **상태:** 적용. 이동 틱 제외/회복 안내 부분은 D-028로 대체됨 (사용자가 10초 대기 단축을 요청함)
- **결정:** tickMs를 10000에서 2000으로 줄이고 콘텐츠 버전을 0.2.2로 올린다. 하트비트 15초·유예 2분·이동 간격 200ms·틱당 회복 1은 유지한다. 현재 플레이 검증용 값이며 최종 밸런스 확정은 아니다.

- **표시:** 최대치·이동한 틱·대기·정지의 회복 안내와 실제 틱 간격/회복량을 현재 상태·콘텐츠에서 계산한다. 코어·세이브 확장은 없다.
- **재검토 조건:** 사용자 실제 폰 재확인과 S2 전체 재미/위험/회복 밸런스 평가.


## D-028 전역 틱을 유지하고 마지막 이동 기준의 회복 분리

- **상태:** 승인·구현. 2026-10-14 사용자가 “그렇게 해”로 마지막 이동 후 회복과 전역 틱 유지 제안을 승인했다. D-025/027의 이동 틱 회복 제외 규칙을 대체한다.
- **문제:** 기존 규칙은 이동을 멈춘 뒤에도 전역 틱 경계에 따라 첫 회복을 2~4초(10초 틱에서는 10~20초) 기다리게 한다. 전역 틱을 이동마다 초기화하면 이후 독/출혈 같은 다른 시간 효과도 미뤄진다.
- **결정:** 전역 time/tick은 gameTime만 진행하고, stamina/recover는 스태미나만 회복한다. 현재 전역 tickMs=2000과 독립 stamina.recoveryIntervalMs=2000이다. 마지막 성공 이동에서 회복 대기만 초기화하며 이후 한 회복 간격마다 회복한다. 실패한 이동은 초기화하지 않는다.
- **구현:** runtime이 주입된 단조 Clock과 단일 Scheduler로 전역 틱·회복·하트비트를 예약한다. 지연 효과는 마감 시각 순서, 동시에는 전역 틱→회복 순서로 처리한다. 회복 액션은 양의 안전한 정수 횟수와 콘텐츠의 구역별 회복량을 사용한다. 시각 측정은 엔진에 넣지 않는다.
- **정지/복원:** 정지/위험 공백에는 두 효과를 모두 멈춘다. 재개/새 세션에서는 부분 시간을 소급하지 않고 전체 간격을 새로 센다. 향후 불러오기 연결은 루프 종료→원자적 Store 복원→루프 시작으로 한다. 브라우저 저장/오프라인 정산은 S3다.
- **호환:** 코어 공개 인터페이스·GameState·세이브 v3·이전 예시는 유지한다. movedSinceLastTick은 보존하되 회복 조건에서 제외한다. time/advanced.recovered는 기존 사건 형태를 보존하며 현재 0이고 실제 회복 사건은 stamina/recovered다. 콘텐츠의 기존 *RegenPerTick 이름은 회복 주기당 양으로 유지한다. 새 간격 필드와 규칙 변경을 contentVersion 0.2.3으로 표시한다.
- **재검토:** 실제 폰 조작, 휴식/습격·지속 피해의 동시 효과/사망 처리 순서, S3에서 전역 시간과 회복 횟수의 정산 중복 방지. 해당 기능을 이번 변경이 구현했다고 기록하지 않는다.


## D-029 S2 휴식·습격의 상태/세이브 확장

- **상태:** 승인·구현됨 (2026-10-15). 사용자가 구체 변경안에 “ㅇㅋ ㄱㄱ”라고 승인했다. 아래 코어/세이브/플레이 연결을 적용하고 검증했다.
- **근거:** CLAUDE.md 6.11은 코어 공개 인터페이스/핵심 구조 변경의 사전 제안·승인을, 10절은 세이브 형식 변경의 승인·버전 상승·이전 변환·왕복 검사를 요구한다.
- **문제:** 휴식 여부와 팝업을 닫아도 남는 미처리 습격을 React 상태에만 보관하면 이동·회복·복원 경로가 서로 다른 게임 상태를 보게 된다. 엔진 상태에 보관해야 한다.
- **승인된 상태:**

```ts
type CharacterState = Readonly<{
  position: MapPosition | null;
  stamina: StaminaState;
  movedSinceLastTick: boolean;
  activity: 'waiting' | 'resting'; // 새 필드
}>;
type ExpeditionState = Readonly<{
  pendingAmbush: null | Readonly<{
    triggeredAt: number; // 발생한 gameTime의 안전한 정수
    activityAtTrigger: 'waiting' | 'resting';
  }>;
}>;
```

- character와 expedition의 기존 null을 유지한다. 새 캐릭터는 waiting으로 시작한다. 현재 미구현인 원정 수명 주기를 이번 단위에서 확정하지 않고, 습격이 처음 발생할 때 필요한 expedition 객체를 만든다. 처리 후 pendingAmbush=null로 둔다. 현재 위치/구역은 기존 상태에서 조회하며 중복 저장하지 않는다.
- **세이브:** 기존 v3 스키마를 schemas-v3.ts로 보존하고 현재 포맷을 v4로 올린다. v3→v4는 non-null 캐릭터에 activity='waiting', 기존 non-null 빈 원정에 pendingAmbush=null만 추가한다. null·자원·위치·탐사·시간·난수·메타데이터는 보존한다. v1→v2→v3→v4 체인과 손상 거부·v4 왕복·휴식/미처리 습격 왕복을 검사한다. 변환은 시간/보상을 진행하지 않는다.
- **검증 경계:** 휴식은 배치된 위험 구역·최대치 미만에서만 유효하다. 미처리 습격은 배치된 위험 구역에서만 유효하고 triggeredAt≤gameTime이어야 하며 activity는 waiting이다. 구조 검증과 실제 콘텐츠/위치 검증을 모두 복원 전에 수행한다.
- **행동:** rest/start·rest/stop, ambush/resolve { result: 'defeated' | 'escaped' }. 휴식은 위험 구역이고 자원이 최대치 미만일 때 시작한다. 시작/수동 중지 시 회복 대기를 전체 간격부터 새로 센다. 전역 틱은 유지한다. 성공한 이동·최대치·습격은 휴식을 끝내고 waiting으로 돌아간다. 실패한 이동은 휴식을 유지한다.
- **판정:** 위험 구역의 전역 틱에서 resting이면 휴식 확률을 적용한다. resting이 아니면 해당 틱에 성공한 이동이 없을 때 대기 확률을 적용한다. 안전 구역/이동 틱/정지/위험 공백/미처리 습격에는 추가 판정을 하지 않는다. 시드 난수만 사용하며 0/1 확률은 난수 없이 확정하고 그 사이 확률은 1회 추첨한다.
- **임시 확률:** 전역 틱당 대기 2%·휴식 10%. 현재 2초 틱에서 평균 판정 간격은 각각 약 100초/20초다. 한 위험 구역만 있는 프로토타입의 공통 기본값이며 지역별 보정은 후속 콘텐츠 확장이다. 플레이 후 조정한다(D-013). 전역 틱에서 현재 콘텐츠 값으로 판정한다.
- **미처리 상태:** 발생한 한 틱까지만 진행하고 휴식을 중단한다. 이번 S2 임시 처리에서는 탐험 틱/회복/추가 판정을 정지한다. 이동·휴식 시작은 엔진에서 거부한다. 팝업은 닫을 수 있으나 미처리 상태는 남고 재열기 버튼을 제공한다. 일반 게임 창은 정지하지 않는 기존 원칙을 유지한다.
- **임시 결과:** ‘물리쳤다’/‘도주했다’는 미처리 상태만 해제하고 결과 사건을 남긴다. 실제 전투/적/피해/전리품/귀환은 구현하지 않으며 두 선택 모두 위치·자원·gameTime을 바꾸지 않는다. 처리 후 새 간격부터 재개하되 수동/설정 정지는 유지한다. S5에서 실제 전투 규칙으로 대체한다.
- **동시·지연:** 기존 마감 시각 순서와 전역 틱→회복 순서를 유지한다. 습격이 먼저 발생하면 같은 시각의 회복과 뒤의 지연 틱도 처리하지 않는다. 일괄 advanceTime은 미처리 습격이 생긴 실제 틱에서 멈추며 난수도 이후 추첨하지 않는다.
- **완료 기준:** 휴식 5 회복·성공 이동/최대치/습격 중단·거부 보존·판정 0/1/경계값·같은 시드 재현·일괄/순차 동일·정지/공백의 시간/회복/난수 보존·팝업 닫아도 행동 제한·수동 정지 유지·v1~v4 변환/왕복. 전체 테스트/타입/빌드/콘텐츠 검증과 데스크톱·390/320 모바일 조작을 수행한다.
- **알림 범위:** 앱 내 습격 안내·재열기 버튼·탭 제목 알림을 제공한다. OS 알림 권한이나 외부 서비스는 도입하지 않는다. 브라우저 백그라운드 복귀는 별도 실제 폰 확인이 필요하다.
- **범위 밖:** IndexedDB·오프라인 정산(S3), 실제 전투/지속 피해(S5), S2 전체 재미의 사용자 완료 판정.

- **검증 결과:** Node 22.22.0에서 468개/28개 파일 테스트·타입 검사·빌드·실제 JSON 5개 콘텐츠 검증 통과. 이전 v3 작성 코드로 만든 고정 예시도 검사했다. 브라우저 1280×900·390×844·320×640에서 휴식 회복·발생·닫기/재열기·키보드 제한·두 임시 결과·수동/설정 정지 유지·재개를 확인했다. 실제 폰/재미 판정은 사용자 확인 대기다.


## D-030 S3 첫 단위: 브라우저 저장·자동 복원

- **상태:** 기존 승인 계약 구현됨. PR #13 병합 후 사용자의 다음 단계 지시에 따라 D-001/002/010/020의 브라우저 저장을 연결했다. S2 사용자 재미 판정과 S3 전체 완료는 미확인으로 유지한다.
- **문제:** v4 메모리 왕복만 있어 새로고침하면 탐험이 초기화됐다.
- **결정:** persistence에 네이티브 IndexedDB 저장소와 후보 검증을, runtime에 자동 저장/시작 복원을 둔다. 새 의존성·코어 변경·SaveFile 버전 변경은 없다.
- **저장소:** last-vigil 데이터베이스 구조 버전 1, save-slots의 primary·backup·generation. DB 버전/세대 번호는 SaveFile의 schemaVersion/revision과 구분한다. 검증된 직전 세이브와 새 문자열·세대 번호를 하나의 readwrite 트랜잭션으로 쓴다. 세대가 달라지면 다른 탭의 최신 저장을 덮어쓰지 않는다.
- **시작:** 두 슬롯이 모두 없을 때만 새 게임을 만든다. primary의 JSON/변환/구조/실제 콘텐츠·활동 검증이 실패하면 backup을 검사한다. 백업 복원 뒤 처음 쓰기에서도 그 유효한 백업을 보존한다. 둘 다 실패하거나 미래 버전이면 게임 시작을 막고 기존 데이터를 보존한다. IndexedDB를 사용할 수 없으면 명시적 안내와 메모리 플레이를 제공한다.
- **자동 저장:** 기존 D-010의 1초 디바운스와 visibilitychange hidden 시 즉시 저장 요청. 동시 요청은 직렬화한다. saveId는 첫 생성 시 브라우저 UUID를 사용하고 복원 시 기존 것을 유지한다. revision은 성공한 쓰기에만 증가한다. 실패 시 이전 저장·메타데이터를 유지하고 자동 반복 재시도를 멈추며 UI의 명시적 재시도를 제공한다.
- **경계:** 저장/복원 자체는 gameTime·스태미나·난수·settledUntil을 변경하지 않는다. 시작 뒤 기존 루프의 heartbeat/실시간 진행은 별도다. 팝업·수동 정지·부분 틱은 저장하지 않고 기존 activity/pendingAmbush는 보존한다. React 효과 정리는 실제 페이지 종료가 아니므로 자동 즉시 쓰기를 유발하지 않는다.
- **실패 보호:** 쓰기 중 용량 오류는 트랜잭션을 취소한다. 여러 탭의 충돌은 재시도로 강제 덮어쓰지 않는다. 다른 탭 기록을 불러오려면 새로고침이 필요하다. 직접 사용자의 데이터를 삭제하거나 새 게임으로 덮어쓰는 UI는 추가하지 않았다.
- **검증:** 새 자동 저장 7·후보/시작 복원 9개 테스트, 관련 UI 포함 25개 통과. 저장 경계 변경이므로 마지막 전체 484개/30개 파일·타입 검사·빌드 통과. JSON/콘텐츠/세이브 스키마를 바꾸지 않아 콘텐츠 CLI 재실행은 생략했다. 실제 IndexedDB에서 1280×900·390×844·320×640의 클릭/모바일 이동 터치·새로고침·휴식/pending 복원·합성 숨김 이벤트·백업 복구·용량 오류/재시도·두 슬롯 손상 보존·두 탭 충돌·저장 불가 메모리 안내를 확인했다.
- **한계:** 모바일 강제 종료가 숨김 쓰기를 완료하기 전에 일어나면 최근 변경을 잃을 수 있다. 실제 폰 종료/백그라운드 확인은 미검증이다. 출처(origin)가 다른 Pages 미리보기와 main은 저장소를 공유하지 않는다. 파일 이동 UI는 다음 단위다.
- **범위 밖:** time/settle·거점 오프라인 회복·24시간 상한·즉시 귀환·내보내기/가져오기. 오프라인 연결 시 savedAt/settledUntil과 실시간 진행의 중복 정산을 따로 검증한다. 즉시 귀환 제약은 아직 확정하지 않는다.


## D-031 S3 두 번째 단위: 거점 오프라인 정산과 실시간 중복 제외

- **상태:** 기존 승인된 오프라인 규칙과 이번 개발 지시를 구현했다. 핵심 게임 규칙·코어 공개 구조·SaveFile 형식은 변경하지 않는다. PR #14의 main 병합을 GitHub에서 확인했다(c45a0d1). S2 사용자 판정·S3 전체는 완료로 간주하지 않는다.
- **문제:** 실시간 루프는 settledUntil을 진행하지 않으므로 정산 시작점을 기존 settledUntil만으로 잡으면 저장 전 실시간 진행까지 다시 지급한다. savedAt만 사용해도 시각 역행 후 저장에서는 마지막 실행보다 이른 구간이 생길 수 있다.
- **구현:** time/settle에 from/to를 주입한다. 시작 복원은 from=savedAt, 실제 시작점은 max(from, settledUntil, lastActiveAt)이다. 양의 구간을 콘텐츠 최대 24시간으로 제한하고, 안전 구역에서 전역 틱과 회복 주기를 각각 계산해 기존 advanceTime/stamina/recover 경로를 쓴다. 상한 초과분도 to까지 소비하고 부분 시간은 이월하지 않는다(D-028). 역행/동일 시각은 무변화, 위험지대/미배치/미처리 습격은 지급/습격/난수 소비 없이 기준만 갱신한다.
- **실행 공백:** 일반 실시간은 단조 시계를 유지한다. 유예를 넘긴 안전 구역 공백은 마지막 실행 완료 이후만 같은 정산 경로로 처리한다. 위험지대의 기존 공백 정지는 유지한다. 보이기 이벤트가 정산과 실시간 따라잡기를 각각 중복 실행하지 않도록 다음 타이머/입력이 단일 pump를 사용한다.
- **저장 순서:** 후보 검증→Store 복원→정산→정산 결과 저장 시도→루프 시작. main의 동일 루프를 UI/자동 저장에 주입하고 beforeSnapshot에서 미처리 실행분을 반영한 뒤 상태와 savedAt을 캡처한다. 정지 중 변경이 없어도 숨김 이벤트는 체크포인트를 저장한다. 초기 정산은 저장 구독 전의 변경이므로 settledUntil 차이를 dirty로 감지한다.
- **실패/호환:** 저장 실패/탭 충돌 시 기존 슬롯을 보존하고 기존 안내/재시도를 쓴다. 재시도는 정산을 다시 하지 않는다. v4 및 v1~v3 변환, 콘텐츠 0.2.4, DB 구조 1은 유지한다. 오래된 백업의 회복은 그 백업의 상태/시각부터 계산한다.
- **범위 밖:** 파일 이동·귀환 제약/버튼·야영지 보호 만료·제작/채집 완료·실제 전투. 향후 만료/지속 효과는 마감 순서로 시간·회복을 조합해야 하며 현재 안전 구역 일괄 처리를 그대로 확장하지 않는다. 실제 폰 확인과 재미/위험 판정은 별도다.


## D-032 입력 반응 제보에 따른 임시값/버튼 처리 조정

- **상태:** 임시. 사용자에게서 간헐적으로 키를 눌러도 이동하지 않는다는 제보를 받았다. D-013의 플레이 피드백 기반 임시값 조정이며 새 코어 구조/세이브 계약/핵심 게임 규칙을 추가하지 않는다.
- **관측:** Chromium에서 150ms 방향키 재입력이 기존 200ms 제한으로 거부됨을 재현했다. 터치 버튼은 손가락을 뗄 때의 click까지 이동을 미뤘다. 사용자 환경의 모든 지연 원인을 확정한 것은 아니다.
- **적용:** minimumMoveIntervalMs=100으로 임시 조정, 콘텐츠 0.2.5. MapScreen 이동 버튼은 primary 왼쪽 pointerdown에 즉시 반응하고 포인터 click 중복은 제외한다. click(detail=0)으로 실행되는 Enter/Space/보조기술 경로는 유지한다. 일반 방향키/WASD 연결·최소 간격 검증·스태미나 비용/회복·습격·저장·SaveFile v4는 유지한다.
- **대안/이유:** 입력을 예약하는 큐는 손을 뗀 뒤의 이동을 추가할 수 있어 도입하지 않았다. 제한을 없애면 키 반복 속도에 따라 이동이 폭주할 수 있어 100ms 제한을 유지한다. 이동 버튼의 누르고 있기 자동 반복도 추가하지 않는다.
- **검증/재검토:** 기존 200ms 경계 검사를 지우지 않고 100/200/500ms로 확장했다. 실제 Chromium의 키/마우스/모바일 터치·키보드 버튼 실행·정지 게이트를 확인했다. 실제 사용자 체감에 따라 100ms를 다시 조정할 수 있으며 최종 밸런스 확정이 아니다.


## D-033 키보드·화면 버튼의 길게 누르기 반복 (D-036에서 제거)

- **상태/근거:** 사용자 승인(“그렇게 수정해줘”). 연타 개선은 사용자가 확인했지만 길게 누를 때의 지연을 제보했다. D-032의 “자동 반복을 추가하지 않는다” 부분을 대체한다. 100ms 임시 최소 간격과 포인터 누름 즉시 반응은 유지한다.
- **문제:** 기존 키보드는 OS 반복 시작 지연/반복 속도에 의존했다. 반복 이벤트를 다시 100ms 간격으로 거부하므로 실제 이동 간격도 입력 설정에 따라 달라졌다. 화면 버튼은 한 번만 이동했다.
- **선택:** runtime/input.ts에서 누른 입력만 관리한다. 첫 누름은 즉시 시도하고 이후 콘텐츠 minimumMoveIntervalMs(현재 100ms)마다 기존 loop.move를 호출한다. OS repeat는 무시한다. 세이브/콘텐츠 스키마/코어/전역 틱/회복은 바꾸지 않는다. 지연된 콜백도 한 칸만 시도하고 다음 간격을 새로 예약한다.
- **방향/종료:** 복수 입력은 마지막 누른 방향을 우선하고 해제하면 아직 누른 방향을 다음 간격부터 시도한다. 마지막 입력 해제, 포인터 취소/캡처 손실, 창 이탈/숨김/페이지 이탈, 편집 영역 초점, 다른 키 명령, 세션 정지/설정창/습격, 언마운트에서 해제한다. 벽/자원 부족도 반복을 끝낸다. 자동 재개 없이 새 누름이 필요하다. 쿨다운만 거부된 경우 누르는 동안 다음 주기를 기다린다.
- **포인터/접근성:** primary 왼쪽 누름과 pointer capture로 버튼 밖 해제를 받으며 window의 pointerup/cancel도 처리한다. 이동 버튼에 한해 터치 스크롤/텍스트 선택/길게 누르기 메뉴를 억제한다. 포인터 click 중복을 막고 Enter/Space/보조기술 click(detail=0)은 기존 단일 실행을 유지한다.
- **검증/한계:** 입력 수명·취소 콜백·다중 키·정지/습격과 Chromium 1280/390/320px의 실제 키/터치를 검증했다. 전체 530개·타입·빌드 통과. 상세 결과는 progress/features에 기록한다. 실제 사용자 기기의 길게 누르기 체감과 S2 재미·위험 평가는 별도 미확인이다. 100ms는 최종 밸런스 확정이 아니다.


## D-034 세이브 파일 내보내기·가져오기

- **근거:** 승인된 S3 파일 교환 계획과 사용자의 다음 작업 지시. PR #17의 main 병합(1d57b24/트리 d419f01)을 확인했다. 사용자는 100ms 유지에 동의했으며 별도 수치 변경은 없다.
- **선택:** 설정 정지 안에서 현재 탐험의 v4 JSON을 다운로드하고 파일을 읽어 검증/미리보기한 뒤 명시적 버튼으로 교체한다. 후보 읽기/취소/검증 오류는 현재 탐험을 바꾸지 않는다. 10MiB 파일 상한은 읽기 보호용 임시 설정이며 SaveFile/콘텐츠 계약이 아니다.
- **시간/메타데이터:** 내보내기는 현재 실행분/시각과 마지막 성공 revision을 캡처하며 브라우저 쓰기/revision 증가/별도 정산을 하지 않는다. 가져오기는 incoming.savedAt 기준 기존 정산을 후보 Store에서 한 번 수행하고, 파일 saveId·revision+1·현재 savedAt/콘텐츠 버전으로 기록한다. source ID/revision과 로컬 generation은 섞지 않는다.
- **보존:** 진행 중 쓰기를 기다리고 자동/숨김 쓰기를 막은 뒤, 미저장 현재 진행도 포함한 backup과 새 primary를 기존 원자적 세대 확인 쓰기로 기록한다. 저장 실패/다른 탭 충돌 시 활성 상태/저장 메타데이터/슬롯을 보존한다. 파일을 다시 적용하는 것과 기존 탐험의 저장 재시도를 구분한다. 기존 1개 백업은 이후 자동 저장으로 회전한다는 점을 확인 화면에 알린다.
- **루프:** 성공 후 동일 Store에 복원하고 resetAfterRestore로 이전 탐험의 실행 완료 시각/부분 주기/이동 제한을 지운다. 수동/설정/공백 정지와 새 습격 제한은 보존한다. 이전 탐험에서 미래 시각을 경험한 뒤 시각 역행/파일 교체해도 새 탐험의 이후 구간이 정산에서 빠지지 않게 한다.
- **저장소 불가:** 메모리 가져오기/파일 내보내기를 제공하고 브라우저 저장/백업 불가를 표시한다. 세이브 v4·v1~v3 변환·콘텐츠 0.2.5·DB 구조 1·코어·회복/비용/습격 규칙은 유지한다. 새 의존성은 없다.
- **범위 밖:** 최초 복원 실패 화면의 파일 복구·서버/인계 코드·콘텐츠 버전별 추가 호환성 정책·귀환. 실제 폰 파일 선택/다운로드 및 S2 재미/위험·S3 전체 판정은 별도 미확인이다. 자동/브라우저 검증 결과는 progress/features에 기록한다.


## D-035 거점 즉시 귀환

- **승인:** 사용자가 전투 중 귀환 불가를 제안하고, 미처리 습격 포함·승리/도주 성공 후 허용·스태미나 0 허용·추가 비용/준비/재사용 대기 없음·자원/탐사 유지·도착 즉시 회복 없음의 추천안을 승인했다. 기존 game-design 19장의 준비 몇 틱 제안은 채택하지 않는다.
- **목적지/범위:** 현재 단일 맵에서 콘텐츠의 시작 칸(임시 거점)을 사용하며 이동 가능한 안전 구역인지 검사한다. 여러 맵/거점 중 임의 선택은 하지 않는다. 안전 구역에서는 귀환이 필요 없으므로 비활성화한다. 여러 거점/맵의 귀환 정책은 후속 설계다.
- **엔진:** `map/return`으로 위치를 바꾸고 휴식을 끝내며 이동 표시를 남긴다. 자원·게임 시간·난수·기존 탐사/원정은 보존한다. 유효 가져오기 상태에 거점 기록이 없다면 도착 칸만 추가한다. 미처리 습격은 팝업 열림과 독립적으로 거부한다.
- **실시간:** 귀환 요청 전 이미 마감된 틱/습격을 처리한다. 그 경계에서 습격이 나면 귀환은 차단한다. 성공 후 회복 주기만 새로 세고 전역 틱/하트비트는 유지한다. 추가 게임 시간/자원/재사용 대기는 없다. 기존 일반 이동 간격은 유지하되 귀환에 적용하거나 귀환으로 새로 소비하지 않는다. PR #19 당시 UI는 누른 이동 입력을 지웠다. D-036에서 자동 반복 객체를 제거했으며, 이후 OS 키 이벤트는 일반 이동 입력으로 처리한다.
- **호환:** SaveFile v4·v1~v3 변환·콘텐츠 0.2.5/맵 1·DB 1 유지. 새 코어 상태나 의존성을 추가하지 않는다. 기존 자동 저장·내보내기/가져오기·거점 오프라인 정산으로 귀환 결과를 보존한다.
- **전투 연결:** 현재 구현 가능한 차단 상태는 pendingAmbush다. ‘물리쳤다’/‘도주했다’의 임시 해제 후 귀환을 허용한다. 실제 전투 중 차단과 승리/도주 성공·실패의 구분은 S5의 전투 상태 도입 때 연결한다. 실제 전투를 검증했다고 기록하지 않는다.

## D-038 S4 최소 아이템 순환과 SaveFile v5

- **위임 범위:** 사용자가 상자 획득 → 소지품 확인 → 음식 회복 → 장비 한 종류로 이동 비용 변화의 구현을 지시했다. 이를 위해 필요한 character.inventory·campaign.openedChests와 v4→v5 호환 변환을 함께 구현한다. 제작·상점·복합 옵션·서버·실제 전투는 후속 단계다.
- **콘텐츠:** `item`(이름·설명·태그·정수 g 중량·음식/장비·사용 효과/수정치)과 `chest`(물품 ID·정수 수량·표시 기호)를 구체적인 스키마로 검증한다. 맵 칸의 선택적 chestId가 상자를 참조한다. 전체 맵에서 같은 상자 ID의 중복 배치, 벽 배치, 잘못된 참조·효과를 거부한다. 한 칸의 상자 조회에 전체 맵/상자 목록을 순회하지 않는다.
- **상태/행동:** 수량은 character.inventory.stacks의 아이템 ID별 양의 정수다. equipment.feet는 소지 중인 장비 ID를 참조한다. 장착은 수량을 옮기지 않으며 중량에 한 번만 포함한다. 상자를 여는 현재 행동은 같은 칸에서 물품 전부와 openedChests를 원자적으로 추가한다. 중복 열기는 상태·난수·시간을 보존하며 거부한다.
- **음식/장비:** 제품 효과 목록 `inventory/effects.ts`의 stamina/restore를 런타임 로더·CLI·음식 행동이 공유한다. 음식 한 개가 즉시 회복하고 최대치로 제한한다. 최대치에서는 소비하지 않으며, 음식으로 휴식 중 최대치가 되면 대기로 바꾼다. 장비 수정치는 기존 computeValue에 공급하고 고정 증감 다음 탐사 배율을 적용한다. 안전 구역 비용은 유지한다.
- **임시 콘텐츠:** 여행 식량 회복 120/중량 250g, 탐험용 장화 중량 800g/이동 기본 비용 add -2. 보급 상자 (3,1)에 식량 3·장화 1, 폐허 상자 (5,3)에 식량 2. 기본 비용은 미탐사 6→4·탐사 3→2·안전 0이다. 중량은 장착품을 포함해 합산·표시만 하며 미정인 최대 중량/과적 불이익은 추가하지 않는다.
- **창/시간:** 소지품 창은 일시정지를 켜지 않는다. 회복·습격 판정을 유지하고 습격이 나면 창을 닫아 기존 팝업을 표시한다. 창 안의 방향키는 지도에 전달하지 않는다. 아이템 입력 전 마감된 시간 처리를 먼저 해 경계의 습격을 회피하지 못하게 한다. 일시정지/설정/공백 정지/미처리 습격 중 사용·장착·상자 획득은 차단한다.
- **저장/검증:** 콘텐츠 0.3.0·SaveFile v5, 맵 버전 1·DB 구조 1. v4 스키마를 별도 보존하고 v1~v4를 순서대로 변환한다. 새 필드는 빈 소지품·미장착·빈 상자 기록이며 기존 위치/탐사/시간/난수/자원/휴식/습격/정산 기준을 보존한다. 복원 전 형식 및 실제 아이템·장비·상자 ID/중량을 공통 runtime 검증에서 대조한다. 기존 자동 저장/백업/파일 교환을 그대로 사용한다.
- **한계:** 상자 열린 기록은 현재 캠페인에 보존한다. 원정 재생성/상자 재출현·개별 장비 인스턴스/무작위 옵션·창고·중량 상한은 아직 구현하지 않는다. 최소 UI는 품목별 목록이며 최종 격자형 UI는 후속 작업이다. 사용자 실제 폰/재미 확인을 자동 검사 결과와 구분한다.

- **사용자 선택:** 지도 적 칸 접촉 → 미처리 조우 → ‘전투 시작’. 전열·후열 배치는 와이어프레임 기준. 도주 성공 시 플레이어는 직전 칸, 적은 지도에 남는다. 대기/휴식 습격은 현재 위치에서 시작·도주한다. 기본 공격/방어는 스태미나 0에서도 가능하다.
- **시간:** 전투 중 현실 틱/회복/추가 습격을 중단한다. 행동 선택 시만 턴을 진행한다. 종료(승리/도주/패배)에 진행 턴 수에 비례한 게임 틱을 한 번 더하며, 회복·추가 습격을 소급하지 않는다. 수치는 콘텐츠 임시값이다.
- **행동:** 공격은 명중/피해 난수, 방어는 해당 턴 반격 피해 감소, 기술은 강타 1종, 아이템은 기존 음식 검증/효과 경로, 도주는 확률 판정이다. 실패한 공격/도주도 반격과 턴을 소비한다. 불가능한 행동은 상태·자원·난수를 보존한다. 전열이 살아 있으면 후열은 대상/반격에서 제외하고, 전열 전멸 후 후열이 전투를 이어간다.
- **승패:** 모든 적 처치 시 고정 전리품을 한 번 지급하고 지도 조우를 토벌 기록에 남긴다. 체력 0은 패배와 `character/died` 사건을 남기며 임의 부활/이동/귀환은 막는다. 죽음/유품/새 감시자 계승은 S6에서 연결한다. 결과 확인 후 탐험을 재개한다.
- **저장/재현:** character.health와 expedition의 combat/defeatedEnemies, 지도 미처리 조우의 encounterId/retreat를 추가한다. SaveFile v6, v5→v6는 체력 100/100만 추가하며 null·기존 필드를 보존한다. v1~v5 변환/DB 1/맵 1 유지. 초기 캐릭터/적 배치/콘텐츠 버전/난수/시간과 행동 수열로 같은 엔진을 재생하며 복원 시 결과·자원·위치·난수·시간을 대조한 뒤 교체한다.
- **최소 콘텐츠/한계:** 몬스터 3종, 지도 조우 3개, 고정 식량 전리품. 콘텐츠 0.4.0. 현재 토벌 기록은 원정 객체에 보존하며 귀환만으로 재생성하지 않는다. 원정 생성/초기화 규칙은 후속이며 임의로 적·상자를 리셋하지 않는다. 기존 `ambush/resolve`는 제품 콘텐츠에서 거부한다. 몬스터/조우를 제외한 독립 테스트 콘텐츠에서만 옛 습격 시스템 계약 검사를 위해 남긴다.

## D-042 최근 기록 저장·직업별 마나·지도 비율 조정

- **근거:** 사용자가 이동 기록 제거, 현실 시각 HH:mm, 최근100개 저장/오래된 기록 자동 삭제, 기본4자원/마법사만 마나, 지도 확대/스크롤바 제거/이동 추적, 벽 명도 구분을 요청했다. D-040 화면의 후속 조정이며 캔버스 원본은 수정하지 않는다.
- **기록:** campaign.recentRecords에 현실 시각 epoch ms와 문구를 보존한다. 성공한 Store dispatch의 사건을 한 번 투영해 게임 결과와 함께 공개/자동 저장한다. 상자 품목·수량/음식/장착·해제/휴식/귀환/습격/전투 시작·결과를 기록하고 일반 이동·거부·틱·자동 회복은 제외한다. 마지막100개만 남기며, 시계가 역행해도 사건 순서로 오래된 항목을 지운다. 팝업/컴포넌트 마운트는 기록을 만들지 않는다.
- **시각:** 화면에서는 접속 기기의 현지 시각을 24시간 HH:mm으로 표시한다. 전투 턴/내부 게임 시간은 유지한다. 지연된 타이머의 기록 시각은 사건을 실제 처리한 현실 시각이다. 따라서 늦은 처리와 즉시 처리의 게임 결과·난수는 같아도 기록 시각은 다를 수 있다.
- **호환:** SaveFile v7, 엄격한 v6 스키마/전투 스키마를 보존하고 v6→v7에서 기존 상태를 그대로 옮긴다. 새 기록/직업 자원은 선택 필드이며 없는 과거 세이브는 빈 기록으로 해석한다. 잃어버린 옛 UI 기록을 만들어 넣지 않는다. 자동 저장/파일 교환/재접속이 같은 데이터를 사용하며 콘텐츠0.4.0/맵1/DB1은 유지한다.
- **자원:** 기본 체력/스태미나/정신력/오염도. character.archetype=mage일 때만 마나를 추가한다. 값이 있으면 실제 current/max, 아직 없으면 —를 표시한다. 그 외 직업의 mana 저장은 거부한다. 현재 직업 선택·마나 소모/회복·주문은 추가하지 않는다. 공통 Vitals를 사용하므로 탐험/캐릭터/거점/전투에 같은 조건을 적용한다.
- **지도:** PC 좌우 열을220/248px로 줄이고 중앙 지도를 남은 세로 공간에 맞춘다. 모바일도 화면 높이에 맞춰 영역을 늘린다. 탐험 지도는 수동 팬/스크롤바 없이 이동/리사이즈로 플레이어를 따라간다. 전체 파악은 미니맵이며 전체지도(M)에서는 직접 둘러볼 수 있지만 스크롤바는 숨긴다. 안개/실제 시야 판정/이동 비용은 바꾸지 않는다. 배경#202020, 현재 바닥#626262, 벽#c8c8c8로 구분한다.


## D-043 확인한 길 둘레를 막는 1칸 벽 타일

- **근거:** 사용자가 밝게 돌출된 벽 칸에 X를 표시한 사진과, 이동 불가능한 구역을 다른 색 벽으로 둘러싼 게임 화면을 제공했다. 경계는 빈 사각형 선이 아니라 다른 명도의 실제 벽 타일로 표현한다.
