## D-001 기술 스택

- **상태:** 승인
- **결정:** React + TypeScript + Vite로 만들고, 테스트는 Vitest, 콘텐츠와 세이브 검증은 Zod, 로컬 저장은 IndexedDB를 쓴다.
- **이유:** 바이브 코딩에서 AI가 가장 안정적으로 다루는 조합이다. Vitest는 Vite 설정을 그대로 쓰고, Zod 스키마에서 TypeScript 타입을 만들 수 있어 데이터 구조의 기준을 하나로 둘 수 있다.
- **대안:** 게임 엔진(Phaser 등)은 텍스트·기호 중심 게임에 비해 과하다. Canvas 직접 구현은 UI 패널이 많은 이 게임에 불리하다.
- **재검토 조건:** 격자 맵 렌더링 성능이 CSS Grid로 부족할 때 Canvas 도입을 검토한다.

## D-002 저장은 브라우저 우선, 서버에는 사본

- **상태:** 승인
- **결정:** 게임은 IndexedDB를 주 저장소로 쓰고, 서버에는 백업과 기기 간 동기화용 사본만 둔다. 이동과 전투는 행동 단위로 서버에 보내지 않는다.
- **이유:** 서버 없이도 게임이 완결되어야 하고(명세 1.3절), 서버 비용과 부하를 최소로 줄일 수 있다.
- **대안:** 서버 중심 저장은 비용과 구현량이 크고, 오프라인 플레이가 어렵다. 브라우저 저장만 쓰면 기기 이동이 안 되고, 아이폰 사파리의 7일 저장 데이터 삭제 규칙으로 진행이 사라질 수 있다.
- **재검토 조건:** 플레이어 간 경제나 경쟁 요소를 도입할 때.

## D-003 서버는 Cloudflare 최소 구성

- **상태:** 승인
- **결정:** 정적 사이트는 Cloudflare Pages, 서버 함수는 Workers, 데이터베이스는 D1(SQLite)을 쓴다. 명세 v1.1의 Node.js와 PostgreSQL을 대체한다.
- **이유:** 무료 범위가 넓고, 무료 한도를 넘으면 요금 대신 오류가 반환되어 예상치 못한 비용이 생기지 않는다. 상시 켜진 서버가 없다.
- **대안:** Supabase는 인증과 데이터베이스를 함께 주지만, 무료 프로젝트가 활동이 없으면 자동으로 멈추고 유료 플랜이 더 비싸다.
- **재검토 조건:** 요금제가 바뀌거나, 하루 활동 인원이 무료 한도를 꾸준히 넘을 때. 서버 작업 착수 시 요금을 다시 확인한다.

## D-004 결정론적 엔진

- **상태:** 승인
- **결정:** 게임 규칙은 React와 분리된 순수 로직이다. 상태 변경은 `dispatch`를 거치고, 시간은 런타임이 주입하며, 난수는 상태에 저장된 시드 난수로만 얻는다.
- **이유:** 규칙을 UI 없이 자동 테스트할 수 있고, 오프라인 경과를 실시간과 같은 경로로 처리할 수 있으며, 구울 토벌 기록을 재생해 검증할 수 있다.
- **대안:** UI 컴포넌트 안에서 규칙을 처리하면 처음엔 빠르지만, 테스트와 재현이 어렵고 세션이 바뀔 때마다 구조가 흔들린다.
- **재검토 조건:** 없음. 이 결정을 바꾸려면 아키텍처 전체를 다시 검토해야 한다.

## D-005 플레이어 간 거래·PvP·순위 없음

- **상태:** 승인
- **결정:** 플레이어 간 거래, PvP, 순위 경쟁을 만들지 않는다. 서버는 게임 결과를 검증하지 않고, 공유 기록을 저장하고 보여 주기만 한다. 구울 공식 토벌은 먼저 기록된 1건만 인정하고 전투 기록을 보관한다.
- **이유:** 세이브 조작의 피해가 본인에게만 돌아가므로 서버 검증이 필요 없다. 서버 구현량과 비용이 크게 줄어든다.
- **대안:** 서버 권위 구조는 모든 행동을 서버가 검증해야 해서 이 프로젝트 규모에 맞지 않는다.
- **재검토 조건:** 순위나 거래 기능을 넣고 싶어질 때. 그때는 해당 기능의 결과가 조작될 수 있음을 먼저 검토한다.

## D-006 `src/runtime/` 디렉터리 신설

- **상태:** 승인
- **결정:** 틱 루프, 일시정지, 하트비트, `visibilitychange`, 자동 저장 예약, `GameStore`를 `src/runtime/`에 둔다.
- **이유:** 엔진은 브라우저 API를 쓸 수 없고, UI는 게임 규칙을 처리하면 안 된다. 둘을 잇는 브라우저 의존 코드가 들어갈 곳이 필요하다.
- **대안:** `src/ui/` 안에 두면 UI와 시간 처리가 섞여 테스트가 어려워진다.
- **재검토 조건:** 없음.

## D-007 수치 수정치 계산 순서

- **상태:** 승인
- **결정:** 기본값 → `add` 합산 → `mul` 곱셈 → 반올림 → 최소·최대 제한. 모든 수치 계산은 `computeValue`를 거친다.
- **이유:** 순서를 하나로 고정하면 어떤 효과가 추가돼도 결과가 흔들리지 않는다. 배율을 곱셈으로 합치면 감면이 여러 개 겹쳐도 0 이하로 떨어지지 않는다.
- **대안:** 퍼센트를 더한 뒤 한 번에 곱하는 방식은 감면이 겹치면 값이 0이 되기 쉽다.
- **장단점:** 단순하고 예측 가능하다. 대신 "다른 배율을 무시한다" 같은 특수 효과는 표현할 수 없다.
- **재검토 조건:** 기획상 이 순서로 표현할 수 없는 효과가 필요해질 때.

## D-008 난수 알고리즘 sfc32

- **상태:** 승인
- **결정:** sfc32를 의존성 없이 `src/engine/core/rng.ts`에 직접 구현한다. 내부 상태(32비트 정수 4개)는 `meta.rngState`에 저장한다.
- **이유:** 짧은 코드로 구현할 수 있고, 내부 상태를 저장·복원하기 쉬우며, 게임 용도로 품질이 충분하다.
- **대안:** 외부 난수 라이브러리는 의존성이 늘고 내부 상태 저장 방식이 제각각이다.
- **재검토 조건:** 난수 품질 문제가 실제로 발견될 때.

## D-009 불변 상태 갱신은 직접 작성

- **상태:** 승인
- **결정:** 새 상태는 바뀐 부분만 새로 만드는 코드를 직접 작성한다. Immer는 쓰지 않는다.
- **이유:** 의존성을 늘리지 않는다. 초기 상태 구조가 작아 직접 작성으로 충분하다.
- **대안:** Immer는 깊은 중첩 갱신이 편하지만 의존성이 늘고, 실수로 원본을 바꾸는 코드와 구분하기 어려워질 수 있다.
- **재검토 조건:** 갱신 코드가 반복적으로 길어지거나, 갱신 실수로 인한 버그가 생길 때.

## D-010 자동 저장 방식

- **상태:** 임시
- **결정:** 행동이 처리되면 1초 디바운스 후 저장하고, 화면이 가려질 때(`visibilitychange`)는 즉시 저장한다. 새 세이브를 쓰기 전에 직전 세이브를 백업 슬롯 1개에 보관하고, 새 세이브를 읽지 못하면 백업을 불러온다.
- **이유:** 행동마다 바로 쓰면 IndexedDB 쓰기가 지나치게 잦다. 백업 1개로 저장 도중 오류에 의한 세이브 손상을 막는다.
- **장단점:** 브라우저가 비정상 종료되면 마지막 1초 이내의 진행을 잃을 수 있다.
- **재검토 조건:** 플레이테스트에서 진행 손실이나 저장 지연이 체감될 때.

## D-011 시간 관련 값

- **상태:** 임시
- **결정:**

| 값 | 임시값 | 위치 |
|---|---|---|
| 1틱의 실제 길이 | 10초 | 콘텐츠의 시간 규칙 |
| 하트비트 간격 | 15초 | 런타임 설정 |
| 하트비트 유예 시간 | 2분 | 런타임 설정 |
| 최대 오프라인 인정 시간 | 24시간 | 콘텐츠의 시간 규칙 |

- **이유:** 브라우저는 백그라운드 탭의 타이머를 1분 단위까지 늦출 수 있으므로 유예 시간은 그보다 길어야 한다. 1틱 10초는 회복 표시가 너무 느리지 않으면서 위험지대 습격 판정 횟수를 다루기 쉬운 크기다. 최대 오프라인 인정 시간은 스태미나가 가득 차는 시간보다 충분히 길면 되고, 방치 작업 완료 판정에는 영향을 주지 않는다.
- **재검토 조건:** 플레이테스트에서 회복·습격 체감이 어색하거나, 백그라운드 탭이 정지로 잘못 판정될 때.

## D-012 스태미나 내부 소수 허용

- **상태:** 대체됨 (D-014)
- **결정:** 스태미나 내부 값은 소수를 허용하고, 화면에는 내림해서 보여 준다. 이동 비용 비교는 내부 값으로 한다.
- **이유:** 1틱 10초 기준으로 틱당 회복량이 소수가 된다(예: 분당 2 회복이면 틱당 약 0.33).
- **대안:** 회복 누적 칸을 따로 두고 정수만 저장하는 방식은 상태 필드가 하나 늘고 계산이 복잡해진다.
- **재검토 조건:** 부동소수점 오차로 경계값 문제가 생길 때. 그때는 정수 단위(예: 스태미나 1 = 내부 100)로 바꾼다.

## D-013 미정 세부 사항은 임시값으로 진행

- **상태:** 승인
- **결정:** 수치, 간격, 문구 같은 세부 사항이 미정이라는 이유로 구현을 멈추지 않는다. 합리적인 임시값을 골라 기록하고 진행하며, 플레이테스트 후 사용자가 확정한다. 핵심 게임 규칙과 기획 방향은 여전히 확인을 받는다.
- **이유:** 프로토타입에서 실제로 굴려 봐야 정할 수 있는 값이 많다. 값이 정해지기를 기다리면 개발이 멈춘다.
- **기록 위치:** 구조나 여러 시스템에 영향을 주는 값은 이 문서에, 그 밖의 임시값은 `docs/progress.md`의 '임시값' 목록에 적는다. `CLAUDE.md` 7절에 같은 규칙이 있다.

## D-014 스태미나는 정수로 유지

- **상태:** 임시 (값은 플레이테스트 후 확정)
- **결정:** 스태미나와 모든 회복량·비용은 정수로 다룬다. 소수가 생기지 않도록 최대치와 틱당 회복량을 정수 단위로 맞추고, 이동 비용도 같은 비율로 조정한다. D-012를 대체한다.

| 값 | 임시값 | 비고 |
|---|---|---|
| 1틱의 실제 길이 | 10초 | D-011과 같음 |
| 최대 스태미나 | 900 | 명세 예시 300의 3배 |
| 거점·야영지 회복 | 틱당 1 (분당 6) | 0에서 가득 차기까지 150분 |
| 위험지대 대기 회복 | 틱당 1 (분당 6) | 거점과 같은 속도지만 틱마다 습격 판정 |
| 위험지대 휴식 회복 | 틱당 5 (분당 30) | 거점의 5배. 0에서 가득 차기까지 30분, 10분 휴식에 300 |
| 미탐사 경로 이동 비용 | 6 | 명세 예시 2의 3배 |
| 탐사 완료 경로 이동 비용 | 3 | 미탐사의 절반 (`mul 0.5`) |
| 안전지대 이동 비용 | 0 | |

- **이유:** 소수 스태미나는 부동소수점 오차와 경계값 비교 문제를 만든다. 정수 단위로 맞추면 상태와 테스트가 단순해진다. 최대치를 3배로 늘린 만큼 이동 비용도 3배로 늘려, 가득 찬 스태미나로 다닐 수 있는 거리는 명세 예시(미탐사 150칸)와 같게 유지했다.
- **대기 회복 속도:** 틱당 정수라는 조건에서 대기를 거점보다 느리게 하려면 거점이 틱당 2 이상이어야 해서 모든 수치가 더 커진다. 그래서 대기는 거점과 같은 속도로 두고, 습격 위험으로 차이를 둔다. 휴식·음식에 비해서는 여전히 느린 보조 수단이다.
- **대안:** 내부 단위를 쪼개는 방식(스태미나 1 = 내부 100)은 소수를 피할 수 있지만 표시와 계산 사이에 변환이 생긴다.
- **재검토 조건:** 플레이테스트에서 회복이나 이동 비용 체감이 어색할 때. 값을 바꿀 때도 정수 조건은 유지한다.

## D-015 개발 환경과 Pages 미리보기

- **상태:** 대체됨 (D-018). 개발 도구 선택을 변경했으며 Git·Pages 운영 방식은 D-018에서 유지한다.
- **결정:**
  - 개발은 주로 Claude Code on the web(클라우드 세션)에서 한다. 저장소는 GitHub 비공개 저장소이고, 작업 결과는 작업 브랜치와 PR로 올린다. `main` 병합은 사용자가 한다.
  - Cloudflare Pages를 GitHub 저장소에 연결해, 변경이 올라올 때마다 미리보기 주소가 자동으로 만들어지게 한다. 빌드 명령은 `npm run build`, 출력 폴더는 `dist`다. 연결은 S0에서 프로젝트를 생성한 직후 사용자가 한다.
  - 주소는 Pages 기본 주소(`*.pages.dev`)를 쓴다. 사용자 도메인 연결과 접근 제한 기능은 쓰지 않는다.
- **이유:** 사용자는 주로 폰에서 작업을 확인한다. 클라우드에서 실행되는 개발 서버는 폰에서 열 수 없고, 빌드 파일을 내려받아 파일로 여는 방식은 실제 웹 환경과 저장·시간 처리가 다르게 동작할 수 있다. Pages 미리보기는 실제 배포와 같은 https 환경에서, 변경마다 자동으로 갱신된다. 정적 사이트라 비용이 없다(D-003, 명세 15.8절의 P0~P1 구성과 같음).
- **대안:** 한 파일 빌드를 내려받아 여는 방식은 아이폰에서 동작하지 않고, IndexedDB와 시간 처리 테스트를 믿을 수 없다.
- **장단점:** 미리보기 주소는 주소를 아는 사람이면 누구나 열 수 있다. 주소를 공유하지 않는 것으로 관리한다.
- **재검토 조건:** 미리보기를 외부에 공개하지 않아야 할 이유가 생기거나, 사용자 도메인이 필요해질 때(S10).

## D-016 Node 실행 스크립트는 Node 내장 TypeScript 실행

- **상태:** 승인
- **결정:**
  - `npm run validate:content` 같은 Node 실행 스크립트는 별도 실행 도구 없이 Node 내장 TypeScript 실행(Node 22.18 이상에서 플래그 없이 동작)으로 돌린다.
  - 스크립트는 루트 `scripts/`에 둔다. `scripts`는 `content`와 `engine`을 import할 수 있고, `src/`는 `scripts`를 import하지 않는다.
  - 이를 위해 모든 TypeScript 코드는 상대 import에 확장자를 붙이고, `import type`을 쓰며, `enum`·`namespace`·생성자 매개변수 프로퍼티를 쓰지 않는다. `tsconfig.json`(`nodenext`, `verbatimModuleSyntax`, `erasableSyntaxOnly`)이 강제한다 (architecture 1.4절).
- **이유:** 새 의존성이 없다. architecture 6장의 "같은 검증 코드를 Node에서 실행한다"를 그대로 따른다. 검증 CLI는 효과 레지스트리(`engine/core`)도 써야 하는데, `content`는 Zod 외에 프로젝트 모듈을 import할 수 없어서(architecture 1.2절) `src/content/` 밖에 둔다.
- **대안:** Vitest로 실행하면 import 규칙은 그대로지만 출력이 테스트 형식이고 `npm test`와 범위를 나눠야 한다. `tsx` 패키지는 가장 간편하지만 새 의존성이다.
- **장단점:** 의존성 없이 단순하다. 대신 import 표기 규칙이 프로젝트 전체에 생기고, Node 22.18 미만에서는 스크립트가 실행되지 않는다 (`package.json`의 `engines`, `.node-version`에 명시).
- **재검토 조건:** Node 내장 실행으로 처리할 수 없는 문법이나 도구가 필요해질 때.

## D-017 코어 처리기 연결과 효과 검증

- **상태:** 승인 (S0 세 번째 단위 제안 승인)
- **결정:**
  - 코어는 시스템을 import하지 않는다. 연결부가 시작할 때 `createDispatcher(handlers)`를 호출해 `dispatch(state, action, ctx)` 형태의 함수를 만든다.
  - 행동·사건의 구체적인 유니온은 시스템별로 정의하고 타입 인수로 전달한다. 행동 종류별 처리기 매개변수 타입은 `ActionHandlers`로 연결한다.
  - 행동 처리기 목록과 개별 처리기는 복사·동결하며 실행 중 등록·제거 기능을 만들지 않는다. 제품의 기본 행동 목록은 S0에서 비어 있다.
  - 효과는 `defineEffect`로 Zod 스키마와 적용 함수를 묶고 `createEffectRegistry`로 고정된 목록을 만든다. 레지스트리는 원시 매개변수를 검증·파싱한 후 적용한다.
  - 콘텐츠를 불러올 때 같은 레지스트리의 검증 함수를 호출한다. 콘텐츠 로더 연결은 S0 네 번째 단위에서 구현한다.
  - 테스트용 행동·효과는 테스트 구성에서만 등록한다. 코드 예외는 일반적인 행동 거부로 숨기지 않는다.
- **이유:** 코어의 의존 방향과 고정 목록 원칙을 지키면서, 실제 시스템이 없는 S0에서도 성공·거부·난수·효과 실행 경로를 검증할 수 있다.
- **대안:** 코어가 시스템을 직접 import하면 의존 방향을 위반한다. 실행 중 등록하는 구조는 필요 이상의 상태와 수명 관리가 생긴다.
- **장단점:** 연결부에서 목록을 조합하는 절차가 필요하지만, 시스템별 행동 유니온의 타입 검사와 독립 테스트가 가능하다. 동적으로 바뀌는 플러그인 구조는 지원하지 않는다.
- **재검토 조건:** 실행 중 시스템을 교체해야 하는 실제 요구가 생길 때.

## D-018 개발 도구 선택과 Git·미리보기 운영

- **상태:** 승인 (사용자 지시, 2026-10-14). D-015를 대체한다.
- **결정:**
  - GPT에서 구현·실행·테스트·디버깅을 우선 진행한다. 사용할 수 있는 실행 환경에서 실제 검증한다.
  - Claude Code 사용은 실행 환경 접근, 브라우저 확인 등 구체적인 비교우위가 확인될 때만 제안한다. 제안에는 넘길 작업 범위와 이쪽에서 해결하기 어려운 이유를 적는다.
  - 해결되지 않은 검증은 그대로 미검증으로 보고한다. 도구를 바꿨다는 이유로 완료 기준을 줄이지 않는다.
  - 결과는 GitHub 작업 브랜치와 PR로 전달하고, `main` 병합은 사용자가 한다. 두 도구가 같은 브랜치를 동시에 수정하지 않는다.
  - Cloudflare Pages 운영은 D-015의 설정을 유지한다: `main` 운영 빌드, 다른 브랜치 미리보기, 빌드 명령 `npm run build`, 출력 `dist`, 기본 Pages 주소 사용.
- **이유:** Claude Code 사용량이 빠르게 소모되는 상황에서 반복 구현·검증을 GPT로 옮기고, 필요한 경우에만 Claude Code를 사용한다.
- **재검토 조건:** 도구의 실행 환경·권한·사용량 조건이 달라질 때.

## D-019 콘텐츠 기반과 실행 환경의 연결

- **상태:** 승인 (네 번째 콘텐츠 단위 진행 위임)
- **결정:**
  - 매니페스트가 버전·시간 규칙 파일·정의 파일 목록을 명시한다. 누락·중복·목록 외 파일은 로딩 오류로 처리한다.
  - 시간·스태미나·하트비트 임시값은 기존 D-011·D-014 그대로 JSON에 저장한다. 이번에 계산 규칙이나 값을 바꾸지 않는다.
  - S0 공통 정의 외피는 id·references·dependsOn·effects다. 일반 참조는 존재만 검증하고, 선행 의존은 순환도 검증한다. 게임별 데이터 필드는 각 시스템에서 정의한다.
  - content는 같은 계층과 Zod만 사용한다. 효과 검증 함수는 연결부가 전달하며 로딩 중 효과를 실행하지 않는다.
  - 브라우저 연결부는 Vite로, Node CLI는 파일 시스템으로 JSON을 수집한다. 두 경로가 같은 순수 로더와 제품 효과 레지스트리 검증 함수를 쓴다.
  - 하나라도 검증 실패하면 부분 DB를 반환하지 않는다. 성공한 DB는 입력과 분리한 뒤 중첩까지 읽기 전용으로 고정한다.
- **이유:** 잘못된 콘텐츠가 실행 단계에 들어가지 않게 하고, 엔진을 import하지 않는 콘텐츠 계층과 브라우저·CLI의 같은 검증 경로를 유지한다.
- **장단점:** 매니페스트에 파일을 추가해야 한다. 대신 검증에서 누락되는 파일과 잘못된 의존 관계를 찾을 수 있고, 데이터 파일 추가만으로 브라우저·CLI가 함께 수집한다.
- **재검토 조건:** 실제 게임별 정의를 도입할 때 공통 외피와 참조 추출 구조를 확장한다. 선택적 의존이나 순환을 허용해야 하는 관계는 dependsOn과 구분한다.
