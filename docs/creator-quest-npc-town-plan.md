# 제작 도구 통합·NPC·퀘스트·마을 포인트 앤 클릭 계획 (초안)

**작성:** 2026-10-21  
**상태:** [9절 초기 정책 확정 / 미구현]. A안은 D-049, 9절 나머지 초기 범위·기본 규칙은 D-050으로 사용자 승인(2026-10-21). 상세 스키마·화면 시안·확장 기능은 구현 단위에서 검증하며, 아직 코드가 추가된 것은 아니다.  
**기준:** `docs/game-design.md` 1.2, 5, 6, 9, 11, 14, 15, 17장; `docs/roadmap.md` S6·S7·S8·T1; `docs/architecture.md`; `docs/map-maker.md`; `CLAUDE.md`.  
**현재 기준선:** S5 전투와 T1 맵·몬스터 제작 기능까지 구현. 퀘스트 진행 엔진·NPC 대화/배치·마을 장면은 미구현. 기본 게임의 퀘스트·코덱스는 빈 UI다.

## 1. 목적과 기획 근거

- 제작자가 엔진 코드를 수정하지 않고 맵, NPC, 대화, 퀘스트를 정의·검증·시험·등록할 수 있도록 한다(기획서 1.2절, 17.6절).
- **위험지역/던전의 격자 탐험과 마을 1개의 포인트 앤 클릭 탐색을 공존**시키는 방향을 확정했다. 이 조작 방식은 기존 기획서에 확정된 규칙이 아니라 2026-10-21 사용자 제안이다.
- 기획서 9.2~9.3절의 거점 유형(마을·요새·전초기지 등)과 NPC 대화·퀘스트 수락/완료, 11.1절의 메인/서브 퀘스트, 11.3절의 조건→텍스트→선택지→결과 모델을 재사용한다.
- 기획서 6장에 따라 캠페인에 남는 진행과 캐릭터 개인 진행을 구분한다. 특히 사망·계승에 앞서 퀘스트 상태의 소유 주체를 설계해야 한다.
- 서버를 요구하지 않는다. 실제 플레이 진행은 기존 엔진·콘텐츠·IndexedDB를 활용한다. **메이커 초안 저장소**와 플레이 **SaveFile 슬롯**은 분리한다.

## 2. 화면 모델: 격자 던전 + 클릭형 마을 (A안 위치 모델 확정)

### 2.1 권장 사용자 경험

1. 던전/필드에서는 기존 격자 지도, 안개, 이동, 적 조우, 스태미나·시간 규칙을 그대로 사용한다.
2. 연결된 마을 입구 또는 거점 접근 지점에서 **명시적으로 입장**하면 마을 화면으로 전환한다. 입구 연결의 구체 입력/전환 조건은 착수 전에 결정한다.
3. 마을은 하나 이상의 **장면(scene)** 으로 구성한다. 배경 위의 클릭 가능한 장소·건물·NPC **핫스팟(hotspot)** 을 선택해 설명, 다른 장면, 대화, 퀘스트, 향후 시설 UI로 이동한다. 캐릭터를 한 칸씩 이동시키지 않는다.
4. 나가기/출입구를 선택하면 연결된 격자 지도의 유효한 좌표로 복귀한다. 모바일에서는 핫스팟과 동등한 목록 선택 UI도 제공한다.
5. 첫 단계는 배경을 이미지로 고정하지 않는다. 텍스트/기호/CSS 레이아웃만으로도 장면을 시험할 수 있고, 이후 정적 이미지 배경 및 좌표 핫스팟을 추가할 수 있게 데이터/표시를 분리한다.

### 2.2 기존 위치·지도와의 호환 — **A안 확정** (D-049)

- **확정:** 마을 진입 지점은 기존 격자 맵의 유효한 입구 좌표를 **앵커(anchor)** 로 유지한다. 별도 마을/장면 콘텐츠를 표시하되 기존 `character.position`의 맵 ID·층·좌표와 탐사 기록을 마을 내부 장소 정보로 변경하거나 재해석하지 않는다.
- 마을 내 **광장·여관·대장간·NPC 선택은 포인트 앤 클릭 UI의 탐색/상호작용**이다. 클릭할 때마다 캐릭터의 격자 좌표를 변경할 필요가 없으며, 건물마다 캐릭터의 물리적 위치를 저장·복원하는 기능은 요구하지 않는다. 재접속 시 여관 2층 같은 마지막 화면으로 돌아가는 기능도 계획하지 않는다.
- **실제 게임 진행과 UI 탐색을 분리한다.** 현재 열어 본 장소/패널은 일시적 UI 상태로 관리해도 된다. 단, NPC와 한 대화 선택, 퀘스트 수락/완료, 보상 지급, 장소 영구 해금처럼 게임에 남아야 하는 결과는 엔진 상태/행동으로 기록하고 저장·복원한다. UI 상태만으로 퀘스트 완료를 처리하지 않는다.
- 마을 **입장·퇴장**, 그리고 실제 월드맵/던전 간 이동은 기존 엔진의 검증된 행동을 통해 처리한다. 출입구를 클릭해 탐험이 필요한 '폐쇄된 지하실'로 진입하는 경우에는 **별도의 격자형 던전 맵**으로 연결하는 방식을 지원할 수 있도록 설계한다. 지하실 내부를 마을의 위치 시스템으로 모사하지 않는다.
- 사용자 결정에 따라 **마을의 낮/밤 전환이나 시간대별 NPC 일정 시스템을 계획하지 않는다.** 이는 기존 게임 시간 틱, 스태미나 회복, 방치 작업 타이머까지 제거한다는 뜻이 아니다. 마을에서의 시간/회복/습격 규칙은 별도 결정 사항으로 남는다.
- 기존 맵/층/좌표/버전, 탐사 기록, 출입구, 거점 오프라인 정산을 파괴하거나 기존 `MapDefinition`을 일괄 변환하지 않는다. A안을 구현하더라도 *퀘스트·NPC 진행 상태* 신설 시에는 해당 상태에 대한 별도 저장/마이그레이션이 필요할 수 있다.
- **B안(격자/장면 통합 위치 타입)은 현재 구현 계획에서 제외**한다. 실제로 물리적 장소별 이동·전투 등 기존 앵커로 해결할 수 없는 요구가 새로 생길 때만 재검토한다.

### 2.3 마을 UI 정보 구조 (표현 원칙 확정, 세부 시안 후속)

- **PC:** 중앙 장면(배경·핫스팟), 한쪽 장소/인물 목록, 다른 쪽 선택 대상의 설명·대화/행동 패널.
- **모바일:** 장면 화면 + 큰 터치 대상, 장소/인물 목록으로 대체 접근, 대화·퀘스트는 하단 시트 또는 독립 화면. 게임 기본 탐험 UI의 한 화면 배치 원칙과 충돌하지 않도록 한다.
- 접근성: 포커스 가능한 핫스팟, 키보드/터치 조작, 이름·상태 설명, 44px 이상 터치 영역, 배경 이미지가 없어도 이용 가능한 목록.
- **표현 원칙:** 장소/건물/NPC 핫스팟을 핵심으로 하고, 배경은 텍스트/CSS/삽화로 교체할 수 있게 한다. 처음에는 기존 회색조·문자 기반 화면으로 시험하며 구체적 디자인은 시안 후 결정한다.

## 3. 데이터 정의·참조 후보 (아직 스키마 확정 아님)

| 후보 정의 | 주요 필드 제안 | 참조·검증 |
|---|---|---|
| `TownDefinition` | id, version, 이름, 입구·출구 링크, 시작 장면 ID | 기존 맵·층·좌표/장면 존재, 왕복 이동 유효성 |
| `TownSceneDefinition` | id, townId, 제목·설명, 배경 표현, 핫스팟 목록 | 장면 간 목적지·NPC·시설·퀘스트 링크 유효성 |
| `HotspotDefinition` | id, 표시명, 위치/클릭 범위 또는 목록 순서, 대상 종류, 노출 조건, 행동 | 같은 장면 내 ID 중복/겹침 경고·대상 참조/조건 검사 |
| `NpcDefinition` | id, 이름·설명, 소속/역할, 대화 시작점, 등장 조건 | NPC 본체와 배치 인스턴스 분리; ID 충돌 검사 |
| `NpcPlacement` | instanceId, npcId, townId/sceneId/핫스팟 또는 격자 좌표, 등장 조건 | 한 NPC의 여러 장면 중복/이동 정책·유효 좌표 검사 |
| `DialogueDefinition` | id, 대사 노드, 선택지, 조건, 결과 참조 | 누락 노드·무한 즉시 전환·고아 노드/순환 경고 |
| `QuestDefinition` | id, 메인/서브, 제목·설명, 개방·수락 조건, 단계·목표, 완료 조건, 보상, 후속 퀘스트, 진행 귀속 | 교차 참조, 조건·효과 레지스트리, 퀘스트 선행 순환, 보상 유효성 |

- 실제 필드명/파일 배치/스키마는 해당 단계에서 Zod + TypeScript로 확정한다. 표를 현재 존재하는 타입이라고 읽으면 안 된다.
- 같은 NPC **정의**와 특정 마을에 등장하는 **배치**를 분리해 기존 몬스터 정의·개별 조우 ID 방식과 유사한 확장을 허용한다. 동일 NPC의 동시 다중 배치 허용 여부는 별도 결정한다.
- 데이터의 **정의(정적 콘텐츠)** 와 NPC 관계·대화 플래그·퀘스트 진행 같은 **플레이어 상태**는 분리한다. 플레이어별 진행을 콘텐츠 JSON에 기록하지 않는다.
- 콘텐츠는 기존 로더의 원자 검증·고유 ID·버전 계약을 따른다. JSON 임의 코드 실행/표현식 평가를 허용하지 않는다.

## 4. NPC·대화·배치: 첫 구현 범위

1. **NPC 정의 편집:** ID/이름/설명/표시 기호·역할/대화 시작점을 제작 폼에서 편집한다. 독립 NPC 메이커 페이지의 필요성은 콘텐츠 수와 UI 시험 후 결정한다. 첫 버전은 통합 제작 화면 안의 NPC 목록·편집 패널로 충분하다.
2. **맵·마을 배치:** 마을 장면의 지정 핫스팟에 NPC를 배치·선택·해제하고, 이후 필요하면 격자 지도의 유효 칸에도 배치한다. 벽·출입구·적 등 기존 배치와 충돌하는 규칙은 사전 정의·검증한다.
3. **대화:** 텍스트 노드, 선택지, 다음 노드 연결, 기본 노출 조건, `quest/offer`·`quest/turn-in` 등 승인된 명령을 작성한다. 대화 개시/선택 결과는 게임 엔진을 통과한다.
4. **게임 시험:** NPC를 선택→대화→조건 충족 시 선택지 노출→퀘스트 수락·보고→대화 종료. 중복 클릭, 취소, 새로고침을 확인한다.
5. **확정된 첫 범위:** NPC 고정 배치·조건부 표시·대화만 구현한다. 이동·사망·이탈·호감도·상점·고용 및 복합 분기는 후속이고 낮/밤 NPC 일정표는 도입하지 않는다. 시설 기능 해금·NPC 생존 정책은 S7에서 설계한다.

## 5. 퀘스트 엔진·메이커: 첫 구현 범위

### 5.1 퀘스트 엔진 없이는 완전한 시험이 불가

- 메이커에서 JSON만 작성하는 것과 게임에서 **수락 → 진행 감지 → 완료 → 보상 → 후속 해금**하는 것은 별개 작업이다.
- S6의 '코덱스·퀘스트 화면 기초'와 연결되는 최소 퀘스트 엔진을 마련한다. S8에 예정된 범용 이벤트 엔진 전체를 앞당겨 만들지 않는다. 초기 퀘스트에 필요한 작은 조건·효과 유형부터 등록하고 나중에 확장한다.
- 진행의 근거는 기존 탐험/조우/전투/아이템 사건과 NPC 대화·입장 사건이다. UI가 보상 지급이나 진행도 증가를 직접 수행하지 않는다.

### 5.2 초기 지원을 검토할 목표·트리거

| 목적 | 첫 단계 지원 후보 | 범위 제한 |
|---|---|---|
| 장소 발견/방문 | 기존 mapId·floor·좌표 또는 townId/sceneId 도달 | 방문 중복 집계 금지 |
| NPC에게 말 걸기 | npcId의 특정 대화 노드·선택지 처리 | '대화 창을 보기만 함'과 실제 대화 완료 구별 |
| 적 처치 | monsterId 또는 **고유 encounterId** 기준 | 동일 처치 중복 집계 금지, 재출현 규칙과 연결 |
| 아이템 확보/전달 | 특정 itemId 보유·획득/소모 | 보유 검사와 누적 획득을 구분, 원자적 소모 |
| 귀환·보고 | 지정 거점/대화에서 완료 요청 | 완료 전 조건 재검증·보상 중복 지급 방지 |
| 제작·시설·방치 작업 | 인터페이스 자리만 계획 | S7/S8의 실제 엔진 구현 뒤 활성화 |

### 5.3 상태·수명 주기 제안

- 기본 상태 흐름 후보: `locked/available/active/completable/completed` 및 조건부 `failed`. 화면 표시 상태와 저장 상태를 분리할 수 있으므로 실제 상태 값은 설계 시 줄인다.
- **초기 범위 확정:** 단계마다 한 목표를 순서대로 진행한다. 동시 목표(AND/OR)·분기·반복·시간 제한은 첫 버전에서 제외하고 나중에 별도 검토한다.
- **두 귀속 유형 확정:** 캠페인 퀘스트는 수락·진행·완료 상태를 사망 후에도 유지한다. 캐릭터 개인 퀘스트는 해당 캐릭터 사망 시 진행을 종료하며 새 캐릭터에게 자동 계승하지 않는다. 개인 퀘스트 재수락 조건은 해당 콘텐츠 정의로 관리한다. 기존 캠페인 완료 기록을 되돌리지 않는다.
- 수락·목표 진행·완료·보상·후속 해금을 엔진 행동/사건으로 관리한다. 재접속·세이브 복원·중복 이벤트 처리에도 보상과 진행이 한 번만 반영된다.
- **중요 퀘스트 물품 처리 확정:** 캐릭터 사망 시 일반 유해 무작위 손실 대상에서 제외하고 캠페인 거점 보관소·기록보관소에 한 번만 안전 귀속해 회수 가능하게 한다. 개인 퀘스트 종료/재수락 과정에서도 중복 생성·영구 진행 불능을 막도록 참조를 검증한다. 보관소 실제 API는 해당 구현 단계에서 설계한다.
- 세이브 상태 조각을 추가하면 SaveFile v8 다음 **새 스키마 버전·단계별 마이그레이션**이 필요하다. 이전 저장과 진행 중 전투 재생을 보존해야 한다. 콘텐츠 버전 변경 정책도 별도 검토한다.

### 5.4 퀘스트 메이커 UI

- 기본 정보 → 발동/공개 조건 → 수락 경로(NPC/장소 등) → 목표 단계 → 완료·보상 → 후속 퀘스트 순서의 편집 흐름.
- 목표는 '유형 선택 → 참조 대상 검색/선택 → 횟수/조건 입력' 폼으로 작성한다. 맵·NPC·몬스터 메이커가 만든 정의를 ID로 참조한다.
- 단계 목록 재정렬·미리보기·완료 가능 여부 시뮬레이션·누락 참조 및 순환 검증을 제공한다.
- 한 번의 제작자 시험 세션에서 '마을 입장→NPC 수락→던전 목표→마을 복귀→NPC 보고→보상 지급'을 확인한다.

## 6. 공통 메이커 UI 및 저장 정책

### 공통 기반

- 맵·몬스터·퀘스트/NPC 화면 사이 내비게이션, 선택 콘텐츠 검색, ID/버전 표시, 문맥별 도움말, 저장 상태·오류·검증 패널.
- 편집 영역을 대화상자보다 **주 작업면 중심**으로 구성한다. 맵은 캔버스+도구/레이어/속성, 몬스터는 능력치+행동 묶음 카드, 퀘스트는 단계·조건·관계, 마을은 장면+핫스팟 목록/속성으로 구분한다.
- 모바일은 큰 입력 영역과 내부 스크롤을 지원한다. 콘텐츠 제작 도구의 화면 구성을 실제 게임 플레이 UI와 혼동하지 않는다.

### 초안과 배포 데이터

- 제작 전용 IndexedDB 영역에 초안 **자동 저장/복원**을 도입할 것을 제안한다. 메이커 초안은 게임 primary/backup/generation 슬롯과 무관해야 한다.
- 현재 JSON 내려받기/불러오기·같은 파일 재시도·불량 파일 시 기존 초안 보존을 유지한다. 가져온 파일의 버전/참조/용량을 검사하고, 충돌은 덮어쓰기 대신 명시적 해결 흐름을 제공한다.
- 배포는 **검증 → 변경 영향 미리보기 → 백업 → 명시적 적용 → PR/배포** 흐름을 따른다. `register:world`의 기본 검사만/--apply 안전 정책을 보존하고, 새 콘텐츠 등록 스크립트가 필요하면 별도 구현한다.
- 기존 맵 지형과 저장 기록을 바꾸는 등록은 현재 호환 보호 정책대로 거부한다. 콘텐츠 교체/마이그레이션의 우회 경로를 만들지 않는다.

## 7. 제안 작업 단위 및 의존성 (로드맵 변경은 승인 전 미확정)

| 단위 | 주요 작업 | 종료 시 직접 확인할 결과 |
|---|---|---|
| C1 공통 메이커 UX | 메이커 진입/공통 저장·복원/검증·JSON 흐름, 맵·몬스터 화면 사용성 정리 | 새로고침 후 편집 초안 복구·파일 교환, 게임 슬롯 불변 |

| C3 NPC·대화 | NPC 정의/배치·대사/선택지 최소 엔진과 편집 UI | 마을 인물과 대화, 조건별 선택지·참조 검증 |
| C4 퀘스트 기초 엔진 | 진행 상태 소유·기초 트리거/목표·수락/완료/보상·마이그레이션 | NPC 수락→던전 목표→NPC 보고, 중복 보상 없음 |

- **순서 추천:** C1 → C2 → C3 → C4 → C5 → C6. 각 단위는 PR 단위로 쪼갤 수 있다. 데이터 계약만 필요한 경우 C3/C4 일부를 병행 설계하되 동시에 대규모 구현하지 않는다.
- **일정 확정(D-050):** C1~C6을 **S6 이전 별도 T2**로 순서대로 구현하고, 각 단위를 독립 PR로 확인·수용한다. T2에서 퀘스트 상태와 사망 경계 계약을 준비하고 S6에서 실제 죽음→새 캐릭터 계승을 검증한다. S7 시설, S8 범용 이벤트/방치 작업을 앞당기지는 않는다.
- NPC 시설 역할·상점/제작·방치 작업 연결은 S7/S8에 남긴다. 완성된 범용 이벤트 편집기·아이템/시설 메이커는 현재 범위에 포함하지 않는다.

## 8. 완료·회귀 검증 체크리스트

### 데이터·엔진 (자동)

- [ ] 존재하지 않는 맵/장면/핫스팟/NPC/대화/퀘스트/아이템/몬스터 ID와 중복 ID를 거부한다.

- [ ] 실패한 클릭/대화/퀘스트 수락·보상 요청은 엔진 상태·아이템·시간·난수를 변경하지 않는다.
- [ ] 동일 사건의 중복 전달, 버튼 연타, 로드 후 재실행에서도 퀘스트 목표/보상을 중복 반영하지 않는다.
- [ ] 캠페인/개인 퀘스트 진행과 NPC 관련 영구 상태는 저장·복원한다. 마을 내 임시 선택 장소는 복원 대상으로 요구하지 않으며, 기존 격자 위치/구형 v1~v8 데이터 변환은 회귀하지 않는다.
- [ ] 같은 상태·시드·행동에서 같은 결과가 나온다. 기존 전투 기록 재생과 메이커 등록 호환 규칙을 유지한다.

### 브라우저·직접 플레이

- [ ] PC·모바일에서 던전↔마을 전환, 클릭 가능한 장소/NPC 목록·키보드 선택·돌아가기를 확인한다. 마을 내부 장소 선택으로 기존 격자 앵커가 바뀌지 않음을 확인한다.
- [ ] 핫스팟 겹침·화면 축소·모바일 회전·safe area·긴 대사·모달 내부 스크롤을 확인한다.

## 9. 확정된 초기 정책 (D-049·D-050)

2026-10-21 사용자가 나머지 항목을 **추천 방향대로 승인**했다. 아래는 *초기 구현 정책*이지 해당 기능 구현 완료를 의미하지 않는다. 메이커 세부 UI와 스키마 명칭은 작업 PR에서 정한다.

| 쟁점 | 확정 방향 | 범위·영향 |
|---|---|---|
| 마을 조작·표현 | **장면+핫스팟 포인트 앤 클릭** | 배경은 텍스트/CSS/이미지로 교체 가능; 구체적 시안은 추후 |
| 적용 장소 | **마을 1개부터 구현·검증** | 다른 모든 안전 거점 자동 전환은 하지 않음 |
| 마을 위치 | **기존 격자 앵커 A안** (D-049) | 건물 선택별 물리 좌표 저장 불필요; 탐험이 필요한 장소는 별도 격자 던전 |
| 장면 전환 비용·시간 | **마을 내부 UI 탐색에 별도 스태미나·게임 틱 비용 없음** | 기존 거점의 실시간 게임 틱/안전구역 회복·오프라인 정산은 계속 적용; 실제 격자 이동/전투 비용은 그대로 |
| NPC | **고정 배치·조건부 표시·대화부터** | 이동·사망·이탈·호감도와 시간대별 NPC 일정은 미도입 |
| 퀘스트 개시·완료 | **NPC를 통해 수동 수락·보고** | 자동 시작/자동 완료는 후속 |
| 퀘스트 귀속·계승 | **캠페인/캐릭터 두 유형** | 캠페인 진행·완료 유지; 개인 진행은 캐릭터 사망 시 종료·미계승 |
| 목표·분기 | **순차 단일 목표 단계** | AND/OR·분기·반복·시간 제한은 후속 |
| 중요한 퀘스트 물품 | **사망 시 거점 보관소/기록보관소로 귀속** | 일반 유해 손실 대상 제외, 중복 귀속·진행 불능 금지 |
| 일정 | **C1→C2→C3→C4→C5→C6을 별도 T2로 S6보다 먼저 실행** | 단위별 PR·테스트·사용자 확인을 거친 뒤 다음 단위 진행 |

**마을 시간 정책의 적용 범위:** 첫 마을은 기존 안전 구역에 연결하며, 단순 장소·NPC 화면 선택은 별도 행동 비용을 요구하지 않는다. 마을 화면을 연다고 이미 작동하는 게임 틱·거점 회복·오프라인 정산을 멈추지 않는다. 기본 마을 장면에서 위험 구역 습격·전투를 임의로 발생시키지 않는다. 특별한 위험 장소는 격자 던전에 연결한다. NPC 대화/퀘스트 효과 중 명시적으로 시간이 소모되는 기능을 나중에 추가한다면 그 효과만 별도 규칙으로 정의한다.

**아직 구현 중 결정할 세부 기술 사항:** 실제 JSON/Zod 타입의 필드명, 메이커 시안, 격자↔마을 진입의 정확한 UI 조작, NPC/퀘스트 진행 상태의 저장 마이그레이션, 거점 퀘스트 물품 귀속을 처리할 원자적 엔진 행동. 사용자가 승인한 정책을 바꾸는 경우에만 다시 기획 결정을 요청한다.
