# roadmap.md — The Last Vigil 개발 계획

단계별 구현 목표, 선행 조건, 완료 기준을 정의한다. 게임 규칙은 `docs/game-design.md`(통합 명세서 v1.2), 구조는 `docs/architecture.md`, 현재 진행 상황은 `docs/progress.md`가 기준이다.

## 0. 이 문서의 규칙

- 단계 계획의 변경은 사용자 승인 후에만 한다.
- 지금 어느 단계에 있는지는 이 문서가 아니라 `docs/progress.md`에 적는다. 이 문서의 상태 열은 단계가 끝났을 때만 바꾼다.
- 각 단계의 규칙과 수치는 명세서를 따른다. 이 문서는 무엇을 언제 만드는지만 정하고, 게임 규칙을 다시 적지 않는다.
- 커밋 메시지의 단계 번호(`[S2]` 등)는 이 문서의 단계 번호를 쓴다.

## 1. 단계 진행 원칙

1. 각 단계는 끝났을 때 직접 실행해 볼 수 있는 결과물을 남긴다.
2. 완료 기준을 모두 충족하기 전에는 다음 단계로 넘어가지 않는다. 중대한 결함(데이터 손상, 진행 불능, 회귀)을 남긴 채 넘어가지 않는다.
3. 다음 단계의 기능을 미리 구현하지 않는다. 단, 나중에 바꾸기 비싼 데이터 구조와 규칙은 S0에서 설계한다.
4. 각 단계가 끝나면 기능 추가 없이 정리만 하는 작업을 한 번 한다. 중복 코드, 비대해진 파일, 문서와 코드의 불일치를 정리한다.
5. 미정인 수치는 임시값으로 진행한다(D-013). 단, 각 단계의 '착수 전 확인' 항목은 핵심 기획 판단이므로 사용자에게 확인한 뒤 시작한다.
6. 완료 기준은 '자동 테스트'와 '직접 플레이'로 나눈다. 직접 플레이 항목은 사용자가 확인한다.

## S0. 뼈대와 코어 계약

**목표:** 코드가 실행되는 최소 뼈대를 만들고, 나중에 바꾸기 비싼 계약(상태 구조, 행동 처리, 효과·수정치, 난수, 저장 형식)을 확정한다.

**선행 조건:** 없음

**만드는 것**

- Vite + React + TypeScript 프로젝트, Vitest, Zod. `CLAUDE.md` 2절의 npm 명령 5개.
- `CLAUDE.md` 3절의 디렉터리 구조.
- 코어(`src/engine/core/`)
  - `GameState` 뼈대: `meta`와 빈 `campaign`, `character`, `expedition` (architecture 2.2절)
  - `Action`, `GameEvent` 타입, `dispatch`와 처리기 목록 (architecture 3.1절)
  - sfc32 난수와 상태 저장·복원 (D-008)
  - `computeValue` (D-007)
  - 효과 레지스트리와 테스트용 효과 1개 (architecture 7.1절)
  - UUID 생성 함수
- 콘텐츠(`src/content/`)
  - 매니페스트(`contentVersion`), 로더 뼈대, 교차 참조 검증 뼈대
  - 시간 규칙 JSON과 스키마: 1틱 길이, 최대 오프라인 인정 시간(D-011), 스태미나 수치(D-014)
  - `npm run validate:content`
- 저장(`src/persistence/`)
  - `SaveFile` 타입과 Zod 스키마, `schemaVersion` 1
  - 버전 변환 체인의 구조(변환 함수는 아직 없음)
  - 메모리 안에서의 직렬화·역직렬화 (IndexedDB는 S3)
- 서버 대비 타입: `CombatLog` 타입 정의만 (architecture 5장, 10장)
- React 진입점: 빈 화면
- Cloudflare Pages 미리보기 연결: 프로젝트 생성과 `npm run build`가 동작하는 첫 단위가 끝나면, 사용자가 Pages에 저장소를 연결한다. 작업 도구와 Git·미리보기 운영은 D-015를 대체한 D-018을 따른다.

**범위 밖:** 맵, 게임 UI, IndexedDB, 실제 게임 시스템

**완료 기준 — 자동 테스트**

- `npm test`, `npm run typecheck`, `npm run build`, `npm run validate:content` 통과
- INV-02: 거부된 행동이 같은 상태 참조를 돌려준다
- INV-04: 같은 입력에서 같은 결과
- INV-05: `GameState` JSON 왕복
- INV-18: 수정치 순서와 무관하게 같은 결과
- `computeValue` 예시: 이동 비용 6, `add -1`, `add +1`, `mul 0.5` → 3
- sfc32: 상태를 저장·복원한 뒤 같은 수열이 이어진다
- `SaveFile` v1: 직렬화 → 역직렬화 → Zod 검증 후 동일

**완료 기준 — 직접 확인**

- Pages 미리보기 주소에서 빈 화면이 뜬다. 폰에서도 확인한다.

**문서:** `docs/features.md`, `docs/progress.md` 생성. `docs/architecture.md`의 구현된 항목을 `[구현됨]`으로 갱신.

## S1. 맵과 시야

**목표:** 손으로 만든 맵을 걸어 다니면 전장의 안개가 걷힌다.

**선행 조건:** S0

**만드는 것**

- 맵·타일·구역 정의의 스키마 (명세 3.1, 5.3~5.4절)
- 손으로 만든 테스트 맵 JSON 1개: 안전지대 구역과 위험지대 구역 포함
- 격자 렌더링(CSS Grid)과 기호 표시 (명세 3.2절의 벽, 바닥, 플레이어)
- 상하좌우 이동 행동(`move/step`)과 벽 충돌
- 탐사 기록과 전장의 안개 (명세 3.3절의 규칙)
- 런타임 최소형: `GameStore`, 키보드 입력 → `dispatch` (architecture 9장)

**범위 밖:** 스태미나, 시간 흐름, 저장, 적

**완료 기준 — 자동 테스트**

- 벽으로의 이동은 거부되고 상태가 바뀌지 않는다 (INV-02)
- 이동하면 탐사 기록이 명세대로 갱신된다
- 안개의 세 상태가 명세대로 전이된다
- 맵 콘텐츠의 참조 검증 (INV-15)
- 엔진 테스트가 브라우저 API 없이 실행된다 (INV-17)

**완료 기준 — 직접 플레이**

- Pages 미리보기에서 맵을 걸어 다니며 안개가 걷히는 것을 확인한다. 폰에서 조작할 수 있는 최소한의 이동 방법(화면 버튼 등)이 있어야 한다.

**완료 기준 점검 (2026-10-14, main `56fde7f`)**

| 기준 | 확인 결과와 근거 |
|---|---|
| 벽 이동 거부·상태 불변 (INV-02) | 통과. `map/actions.test.ts`의 같은 상태 참조·난수 보존 검사, Pages 벽 충돌 확인 |

## S2. 시간과 스태미나 — 핵심 루프 검증

**목표:** 스태미나를 관리하며 다니고, 습격 위험을 감수하며 쉬는 루프가 재미있는지 확인한다.

**선행 조건:** S1

**첫 단위 진행 (2026-10-14, D-025)**

스태미나 상태·목적지/탐사 여부별 이동 비용·자원 부족 거부·advanceTime/time/tick·이동 틱 회복 제외·대기 회복·v3 저장 계약과 v1/v2 변환을 구현했다. 화면에 자원·틱을 표시한다. Node 22.22.0 자동 검사와 세 크기의 실제 브라우저 조작 검증을 통과했다. 첫 단위 당시 시간 행동은 엔진/Store 테스트에서 주입했으며, 실제 자동 틱 루프는 아래 두 번째 단위에서 연결했다. S2 전체 완료 기준은 아직 충족하지 않았다.

**두 번째 단위 진행 (2026-10-14, D-026)**

실시간 Clock/Scheduler·자동 틱(최초 10초, 사용자 요청 후 테스트용 2초)·진행/정지 표시·일시정지·설정창 정지·15초 하트비트·위험지대 공백 정지·최소 이동 간격 200ms를 연결했다. 코어 상태와 세이브 v3는 유지했다. 가짜 Clock 경계 검사를 통과했다. 사용자 승인으로 마지막 이동 후 회복 간격마다 처리하는 독립 회복을 연결했다(D-028). 전역 틱은 이동으로 초기화하지 않는다. 휴식·습격과 사용자 재미 확인이 남아 S2 전체는 완료 처리하지 않는다.

**만드는 것**

- 시간 시스템: `advanceTime`, `time/tick` (architecture 4.1~4.2절)
- 런타임 틱 루프(현재 테스트용 1틱 2초, D-027), 일시정지 버튼과 설정창 정지, 하트비트와 공백 정지 처리 (D-011)
- 현재 상태 표시: 진행, 정지 (명세 13.6절)
- 이동 비용 6/3/0, 탐사 경로 감면을 `computeValue`로 계산 (D-007, D-014)
- 타일당 최소 이동 간격(임시값)
- 스태미나 부족 시 이동 거부
- 대기 회복(독립 회복 주기당 1, D-028)과 위험지대 휴식(주기당 5): 시작, 이동 시 해제 (명세 4.4~4.5절)
- 습격 판정: 대기·휴식 확률(임시값), 습격 팝업과 처리 전 행동 제한 (명세 4.6절). 전투는 아직 없으므로 팝업의 선택지는 임시 처리(예: '물리쳤다', '도주했다')로 둔다.
- 게임 내 창이 열려 있어도 시간이 흐른다 (명세 2.4절)

**범위 밖:** 저장과 오프라인 정산(S3), 전투(S5), 음식(S4)

**완료 기준 — 자동 테스트**

- INV-01: 스태미나가 0 미만이나 최대치 초과가 되지 않는다
- INV-03: 게임 시간이 한 행동에서 두 번 진행되지 않는다
- INV-09: 하트비트 공백 동안 회복과 습격 판정이 없다
- INV-10: 정지 중에는 게임 시간 효과가 진행되지 않는다
- INV-19: 스태미나와 비용이 정수다
- 이동 비용이 `computeValue`를 거친다
- 휴식 중 이동하면 휴식이 해제되고, 습격이 발생하면 중단된다
- 가짜 `Clock`으로 틱 루프를 테스트한다

**완료 기준 — 직접 플레이 (사용자)**

- 스태미나를 관리하며 다니는 것이 재미있는가?
- 휴식의 위험이 체감되는가? '쉴까, 더 갈까'를 고민하게 되는가?
- 이동 간격과 습격 확률의 임시값을 조정하고 결과를 `docs/progress.md` 임시값 목록에 기록한다.
- 재미가 없다고 판단되면 S3로 넘어가기 전에 설계를 수정한다.

## S3. 저장과 거점 오프라인

**목표:** 창을 닫았다 열어도 이어지고, 거점에서는 닫아 둔 동안 회복이 쌓인다.

**선행 조건:** S2

**착수 전 확인:** 즉시 귀환의 제약 (명세 19장 '즉시 귀환 제약')

**만드는 것**

- IndexedDB 저장: 1초 디바운스, 화면이 가려질 때 즉시 저장, 백업 1개 (D-010)
- 불러오기 경로: 형식 확인 → 버전 변환 → 검증 → `time/settle` (architecture 8.2절)
- 오프라인 정산 `time/settle` (architecture 4.3절)
- 세이브 내보내기·가져오기
- 안전지대 진입과 즉시 귀환 (명세 4.11절)
- 현재 위치의 시간 규칙 표시 (명세 13.6절)

**완료 기준 — 자동 테스트**

- INV-06: 저장·불러오기 왕복에서 상태와 게임 시간이 그대로다
- INV-07: 같은 시각으로 두 번 정산해도 결과는 한 번과 같다
- INV-08: 기기 시각이 뒤로 가도 자원과 시간이 변하지 않는다
- 최대 오프라인 인정 시간(24시간) 상한
- 손상된 세이브는 거부되고 백업으로 복구된다
- 형식이 다른 파일 가져오기는 거부된다

**완료 기준 — 직접 플레이**

- 거점에서 창을 닫고 몇 분 뒤 열면 회복이 쌓여 있다.
- 위험지대에서 창을 닫았다 열면 그동안은 정지로 처리된다.
- 세이브를 내보냈다가 다시 가져올 수 있다.

## S4. 아이템과 효과

**목표:** 공통 효과 시스템이 실제 콘텐츠를 처리한다.

**선행 조건:** S3

**만드는 것**

- 아이템 정의 스키마와 태그 (명세 8.3절)
- 휴대 인벤토리와 소지 중량, 인벤토리 UI (명세 13.2절)
- 맵 위 아이템 줍기(보물 상자)
- 소비 아이템 사용, 음식의 스태미나 즉시 회복 효과 (명세 4.10, 10.4절)
- 장비 장착과 수정치 공급(예: 탐사 경로 이동 비용 감소 장비 1종) (명세 8.4절)

**완료 기준 — 자동 테스트**

- INV-16: 등록되지 않은 효과나 잘못된 매개변수는 콘텐츠 검증에서 실패한다
- 음식 효과가 효과 레지스트리를 거친다
- 회복이 최대치를 넘지 않는다 (INV-01)
- 장비의 수정치가 `computeValue`에 반영된다
- 소지 중량 규칙이 명세(또는 기록된 임시값)대로 동작한다

**완료 기준 — 직접 플레이**

- 상자를 열어 줍고, 음식을 먹고, 장비를 장착해 이동 비용이 바뀌는 것을 확인한다.

## S5. 전투

**목표:** 탐험 → 습격·조우 → 전투 → 전리품의 순환이 돈다.

**선행 조건:** S4

**착수 전 확인 (핵심 기획 판단, 명세 19장)**

- 전투 진입 조건 (접촉인지, 감지 범위인지)
- 전투 화면 배치 (격자인지, 전열·후열인지)
- 도주 후 처리
- 전투가 게임 시간에 반영되는 방식
- 전투 중 스태미나 고갈 처리
- 원정마다 다시 굴려지는 것 (적 배치와 전리품)

**만드는 것**

- 별도 전투 화면과 턴제 행동: 공격, 방어, 아이템, 도주, 대기. 기술은 최소한만 (명세 8.1절)
- 몬스터 3종의 콘텐츠와 지도 표시 규칙 (명세 3.2, 8.2절)
- 습격 팝업의 '전투 시작'과 연결
- 전리품 테이블
- 전투 기록 `CombatLog`: 시작 시점 난수 상태와 행동 목록 (architecture 5장)
- 체력 0이 되면 사망 사건을 만든다. 사망 처리 자체는 S6.

**완료 기준 — 자동 테스트**

- 같은 `CombatLog`를 재생하면 같은 전투 결과가 나온다
- 조건이 맞지 않는 전투 행동은 거부되고 상태가 바뀌지 않는다
- 전리품 지급이 한 번만 일어난다

**완료 기준 — 직접 플레이**

- 몬스터 3종과 싸우고, 도주하고, 전리품을 얻는다.
- 습격 팝업에서 전투로 넘어가는 흐름이 자연스러운가?

## S8. 방치 작업

**목표:** 채집을 걸어 두고 현실의 일을 하다 돌아와 결과를 확인하는 리듬이 동작한다.

**선행 조건:** S7

**착수 전 확인:** 채집 중 캐릭터 규칙 (명세 19장 '채집 중 캐릭터')

**만드는 것**

- 채집지 정의: 탐사를 마친 구역에서만 개방 (명세 10.10절)
- 채집 작업과 타이머 길이 선택(예: 25분, 1시간, 4시간, 8시간)
- 결과 테이블과 실패 결과의 범위
- 이벤트 엔진 최소형: 조건 → 텍스트 → 선택지 → 결과 (명세 11.3절)
- 작업 결과에 붙는 선택 이벤트
- 시설 생산 1종
- 진행 중인 방치 작업 표시 영역 (명세 13.6절)

**완료 기준 — 자동 테스트**

- 명세 17.8절 시나리오
- INV-11: 방치 작업 결과는 한 번만 지급된다
- INV-12: 방치 작업으로 영구 사망이 일어나지 않는다
- 오프라인 중 끝난 작업이 `time/settle`에서 완료 처리된다

**완료 기준 — 직접 플레이**

- 25분짜리 채집을 걸고 창을 닫았다가, 끝난 뒤 돌아와 결과와 이벤트를 확인한다.
- 하루 1~2회 접속과 진득한 탐험이 함께 성립하는지 느껴 본다.
